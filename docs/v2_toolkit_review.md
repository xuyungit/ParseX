# 工具包重新设计：从任务出发（2026-09-27，第二稿；用户确认后已实施，Q85；接口定型见 §11，Q86）

第一稿（git 历史中）是在现有 13 个工具上改名、分组，用户认为层级仍不一致、冗余、细碎、不成体系，要求不受现有设计影响，从第一性原理重新分析：一个 Agent 要完整处理一份文档，到底需要什么工具；工具之间是否一致、有没有歧义。

## 0. 结论

Agent 只需要四个工具，每个工具对应一件事，名字里写明作用于哪一边：

| 工具 | 一句话 | 改不改文档 | 花不花钱 |
|---|---|---|---|
| `read_draft` | 读我们的解析结果：摘要、待办、文字、大纲、块的细节 | 不改 | 不花 |
| `view_source` | 看原件：取页面或局部的图，或让视觉模型、识别引擎读图，得到一条"证据" | 不改（只存下证据） | 读图的方式花钱 |
| `edit_draft` | 修改解析结果：一组操作，每条写明对象、理由、证据 | 改（唯一的入口） | 不花 |
| `submit_draft` | 交稿：程序核对账目；通过即完成（产品中随后由程序导出） | 不改 | 不花 |

流水线（现在的 `process`）不是 Agent 的工具：Agent 开始之前，程序已经用它做出了初稿。

"原子化、可自由组合"体现在 `edit_draft` 的**操作**上（替换文字、改单元格、设角色、移动、合并……每条独立，可任意组合，一次提交多条），而不在工具的个数上。

## 1. 从任务出发：Agent 在做什么

把 Agent 看作一位校对编辑：左边是原件（页面图像），右边是初稿（程序的解析结果），手边有一张程序列出的疑点清单。编辑做的事只有五种：

1. **了解全貌与待办**：这份文档有多少页、哪些处理完了、还剩哪些疑点；
2. **读初稿**：从头到尾读，或者翻到某处、查某句话、看某张表的每一格；
3. **看原件**：对照原件的某一页、某一块、跨页处，必要时请人（视觉模型）帮忙读图；
4. **改初稿**：改字、改表、补漏、调整标题与顺序、合并与拆分、删掉不该出现的东西；或者确认某个疑点不需要改；
5. **交稿**：确认账目平衡，完成。

这五件事里，第 1、2 件读的都是初稿，第 3 件读的是原件，第 4 件是唯一修改，第 5 件是收尾。所以工具按"**初稿 / 原件**"两个对象、"**读 / 改 / 交**"三种动作组织，得到上面四个工具。

## 2. 设计规则

1. **两个对象，名字写明**：初稿（draft，我们的解析结果）与原件（source，原始文档的页面图像）。每个工具只作用于一个对象，名字就是"动作_对象"，不会把"读初稿"与"看原件"混淆。
2. **感知与修改分开**：`read_draft`、`view_source` 永远不改初稿；`edit_draft` 是唯一的修改入口，程序的流水线也通过同一组操作修改（记为程序所为），所以"程序不推翻 Agent 的决定"成为同一入口上的一条规则。
3. **每个修改都是同一种形状**：`{op, 对象, 内容…, reason, evidence}`。程序逐条检查，逐条回报"采用 / 拒绝及规则名"。
4. **证据是一等对象**：`view_source` 的每个结果（一张图、一个回答、一次识别）都有编号；改动内容的操作必须引用证据编号，程序据此核对（现在 `correct` 的"看过图"、`review_table` 的接受门都归到这里）。
5. **一套编号**：页 `p3`，块 `b-p003-0012`，待办 `w-…`，证据 `e-…`。所有参数只用这几种编号引用对象。
6. **一个待办来源**：待办只在 `read_draft` 里查；修改的回报只说这次改动新开或关掉了哪些待办。
7. **成本看得见**：只有 `view_source` 的读图方式花钱；读初稿、修改、交稿都免费。
8. **Agent 看不到程序内部的东西**：流水线、`actor`、产品中的导出。

## 3. 四个工具

### 3.1 `read_draft`：读初稿

| `view` | 返回 |
|---|---|
| `summary`（默认） | 文档信息、各页状态、块与待办的计数 |
| `issues` | 待办清单：编号、类别、位置、说明、相关原文；可按类别、页过滤 |
| `text` | 按阅读顺序的文字（现在的 `skim`）：`from` 与 `after` / `before` 翻看，或 `page`、`find`；段落默认只显示开头，`full` 显示全文 |
| `outline` | 排版类别表与所有像标题的行，每行附后文开头；Word 文档附样式与编号 |
| `blocks` | 指定块的细节：表格的每个单元格、状态、各来源的识别结果、坐标 |

文字类结果是紧凑的行：块号、角色（H1…、text、table…）、页、排版类别、文字（段落默认只给开头）。

### 3.2 `view_source`：看原件

一次可以提交多个请求，工具内部并发处理。每个请求：

- **看哪里**：`page`、`block`、`seam`（第 N 页下半与第 N+1 页上半拼接）、`region`（页与坐标）；表格可加 `rows`。
- **怎么看**（`as`）：

| `as` | 做什么 | 结果 | 费用 |
|---|---|---|---|
| `image` | 取图片文件，由 Agent 自己看（仅在 Agent 能直接看图的模式下提供） | 图片路径 + 证据编号 | 无 |
| `answer` | 视觉模型按 `question` 作答 | 回答 + 证据编号 | 有 |
| `text` | 识别引擎读出文字 | 识别结果 + 证据编号 | 有 |
| `table` | 视觉模型按列出的问题重建表格 | 表格候选 + 证据编号 | 有 |
| `description` | 视觉模型描述图片 | 描述 + 证据编号 | 有 |

现在的 `ask_image`、`read --image`、`recognize`、`review_table` 的读图部分、`describe_figure` 的读图部分，都是"用某种方式看原件"，合并到这里。读图只产生证据，不改初稿；要不要用，由 Agent 在 `edit_draft` 里决定。

### 3.3 `edit_draft`：修改初稿

一次提交一组操作；`atomic` 为真时任一条被拒则全部不生效。每条操作都有 `reason`；修改内容的操作必须有 `evidence`（`view_source` 返回的证据编号）。

| 类 | 操作 | 说明（取代） |
|---|---|---|
| 内容 | `replace_text` | 块内某段文字改为图上的写法（`correct` 的正文修改） |
| | `insert_text` | 补入图上有、初稿没有的文字（`correct` 的补入） |
| | `set_cells` | 改表格单元格（`correct` 的单元格修改） |
| | `adopt` | 采用一条证据作为块的内容：识别出的文字、重建的表格、图片描述（`recognize` 的采用、`review_table` 的接受门、`describe_figure` 的写入） |
| 结构 | `set_role` / `set_level` | 角色与标题层级 |
| | `move` | 调整阅读顺序 |
| | `link` / `unlink` | 块之间的关系：续接、图题、脚注…… |
| | `merge_tables` / `split` | 跨页续表合并；在换行处拆块 |
| | `exclude` / `include` | 不输出（文字留在 sidecar）/ 恢复输出 |
| | `mark_pending` | 这一块是不是标题拿不准，结构待定 |
| 待办 | `dismiss` | 看过证据、初稿不需要改，关闭一个待办（`close`） |

程序对每条操作做现在已有的检查：引用存在、层级不跳级、同一编号模式同级、原生数字须有本地读数支持、表格重建须过接受门、程序的提议不推翻 Agent 的决定……拒绝时给出规则名与原因。

### 3.4 `submit_draft`：交稿

程序核对：每页都有处理状态、账目平衡、没有非法引用、没有必须处理而未处理的待办（识别失败的页等）。

- 通过：返回完成；产品中程序随后导出，实验模式按参数导出到 `out/`；
- 不通过：返回挡住交稿的问题，Agent 处理后再交。

现在的 `check`（核对）与 `export`（导出）合为"交稿"一个动作；中途想看进度用 `read_draft summary`。

## 4. 一个待办的完整处理，看四个工具如何配合

表格算术提示 `w-7f3a…`（第 4 页表格第 7 行合计不符）：

1. `read_draft view=issues` → 看到 `w-7f3a…`，位置 `b-p004-0002` 第 7 行；
2. `read_draft view=blocks blocks=[b-p004-0002]` → 看这一行现在的单元格；
3. `view_source block=b-p004-0002 rows=[6,7] as=answer question="第 7 行第 1 列的数值？"` → 回答"67876.11"，证据 `e-19c2`；
4. `edit_draft [{op: set_cells, block: b-p004-0002, cells: [...], reason: "...", evidence: "e-19c2"}]` → 采用，待办 `w-7f3a…` 自动关闭；
   或者图上确实就是这样：`edit_draft [{op: dismiss, issue: w-7f3a…, reason: "原件如此", evidence: "e-19c2"}]`。

标题结构：`read_draft view=outline` → `read_draft view=text` 翻看 → 必要时 `view_source … as=answer` → `edit_draft` 一次提交一组 `set_role` / `set_level`。

## 6. 取舍与风险

- **一个大的修改工具**：操作有 15 种。但形状统一、按类列出，现在的 `apply_structure` 已有 10 种操作，Agent 用了 124 次没有格式问题。好处是所有修改走同一个检查与回报。
- **读图与采用分成两步**：描述图片、重建表格从一次调用变成两次（都可批量）。42 次运行里这两种一共只用了 14 次，大批量的描述由流水线完成；换来的是"看原件永远不改初稿"这条规则没有例外。
- **改动面大**：工具入口、命令行、任务说明、三份 Skill、运行时、审计、测试都要改；内部算法不动。
- **待办编号**：需要新加稳定的编号（由对象、类别与相关原文算出），关闭后内容变化会重新出现，与现在的行为一致。

## 9. 实施时澄清的几点（2026-09-27，用户提问）

1. **"程序"是什么，谁做决定**：程序是我们写的 ParserX 代码，不是另一个决策者，包括四样东西：
   - 流水线：做出初稿，其中的规则是提议，只在没有 Agent 时（固定模式）直接成为结果；
   - 工具：Agent 的手和眼，照做，不判断；
   - 把关：对每次修改检查正确性约束（证据、原生数字、表格接受门、层级合法、账目平衡、不推翻 Agent 的决定），可以拒绝，不判断含义；
   - 信号：待办清单，只指路。

   含义上的判断（是不是标题、字对不对）归 Agent；正确性归把关。"思考的规则"在两处：流水线的启发式规则（Agent 可推翻）与 Skill（写给 Agent 的方法）。
2. **Agent 自带的能力**：Codex 有 shell、脚本、改文件的工具。读和分析可以自由用自己的工具（包括把工具的 JSON 输出交给脚本）；初稿只经 `edit_draft` 修改——初稿不是一个 Markdown 文件，而是一组带来源、证据与账目的块，直接改文件无法核对、可能静默丢内容。直接改工作区会被状态摘要发现，整次运行作废；直接读内部文件会被审计记下。
3. **全文检索**：`read_draft --view text` 的 `find`（不计空格、全半角、大小写）与 `pattern`（正则），搜正文、表格的每一行和图片描述，返回块号（可直接用于修改）。不把初稿导出成纯文本文件给 Agent 自己 grep：文档文字要标成数据（`doc_text`），以防文档里藏着指令。
4. **修改的实现**：既不是 diff / patch，也不是整段替换，而是块上的操作——正文"在块内找到恰好出现一次的片段再替换"（与编程 Agent 的编辑工具同理；找不到或不唯一就拒绝，并说明出现了几次）；表格按单元格坐标；漏掉的文字按页面位置补入；整块重写用 `adopt` 采用一次读数，而不是由 Agent 打出整段。Markdown 只在最后由块渲染出来。

## 11. 接口定型（Q86，2026-09-27，用户同意按此顺序实施）

**目的**：工具的契约只写在一处——请求模型（pydantic）及其说明。命令行参数、任务说明里的工具参考、函数调用的工具定义都由它生成。这样换 Agent 或改用自己的循环时，只换适配层。

**评价时查到的问题**（代码与 s3/s4 运行记录）：

- 生成的 JSON Schema 几乎没有说明（`read_draft` 0 条、`submit_draft` 0 条、`edit_draft` 7 条），含义都在手写的任务说明里，且按命令行写；命令行参数名与字段名不一致（`--from` 对应 `start`）。
- 读和写两套词：`read_draft` 显示 `H2`，写时要 `set_role kind=title level=2` 或 `set_level`。`set_role kind=header` 只改标签，块照样输出（渲染只看状态），要另发 `exclude`。
- `link` 列出 7 种关系，其中 `captions`、`footnotes`、`follows`、`belongs_to_section` 在输出与账目中没有作用，`contains`、`duplicate_of` 只由程序建立；Agent 只用过 `continues`。
- 信封的 `unresolved` 对四个工具永远为空；`edit_draft` 的 `diff` 平均占返回的四成，与 `outcomes` 重复；`submit_draft` 的 `out`、`name` 是程序导出用的。
- 没有"改过什么"的视图：最终报告要 Agent 凭记忆列出改动。
- 任务说明混着两层：任务与方法，以及命令行适配（`./px`、目录规则）。

**设计**：

1. **schema 是唯一来源**
   - 每个请求字段、每种操作都有说明，用中文（与任务说明、Skill 一致）。
   - 请求的顶层仍是一个对象：主流函数调用接口不接受顶层的 oneOf / anyOf。参数属于哪个视图、哪种看法，写在说明里，校验给出错误。这修正了评价中的第 4 项（原想改成按视图区分的联合类型）。
   - 命令行参数由请求模型生成：字段名即参数名（`--start`、`--as`），列表用逗号分隔，`looks`、`ops` 用 JSON（`--looks -`），`--request -` 给出整个请求。
   - 任务说明中的工具参考由 schema 生成；手写部分只留任务、方法、规则。
2. **一套词表**
   - 角色：`H1`–`H6`、`text`、`list`、`caption`、`footnote`、`other`。读（`read_draft` 的 `role`）与写（`set_role` 的 `role`）相同；`table`、`figure`、`formula`、`scan` 只读。
   - `set_role {block, role}` 取代 `set_role {kind, level}` 与 `set_level`；流水线的标题步骤也用它。
   - 页眉、页脚、页码、水印是程序做出的"不输出"标签，不是可设的角色。Agent 用 `exclude` 让一个块不输出、`include` 恢复；恢复这类块、或给它设一个正文角色时，它重新输出。"设成页眉却仍输出"的状态不再存在。
   - 续接：`join {first, second, drop_rows}` 取代 `link continues` 与 `merge_tables`——两段文字在输出中合为一段，两张表合为一张（`drop_rows` 去掉重复的表头行）；`unjoin` 撤销文字的续接（合并的表不能拆开）。其余不起作用的关系类型从 IR 删除。
3. **去掉不起作用的东西**
   - 信封只剩 `tool`、`doc`、`ws_version`、`ok`、`result`、`cost`、`failures`；为空（null）的字段不输出。
   - `submit_draft` 没有参数；导出是程序的步骤 `export`（进程内，不给 Agent）。
4. **改动记录**：`read_draft` 的 `changes` 视图列出已被接受的操作（顺序、操作、对象、改成什么、理由、证据），取自调用记录。最终报告只写交稿结果与未解决项；改动由程序列出。
5. **任务说明分两层**：`agent_task.md` 写任务、方法、规则，与 Agent 无关；适配层说明另写（命令行：`./px` 的用法与目录规则；函数调用：无）。
6. **验证**：写一个最小的函数调用循环，直接用 `tool_schema` 与 `call_tool`，不经 shell，换一个模型跑几篇。它的代码量与遇到的问题就是"接口与 Agent 无关"的检验。评价工具看过程指标（无效请求、按规则的被拒、调用次数、返回字数、用时），质量分数只防退步（10 篇各一次，单篇波动 0.02–0.1）。

**顺序**：第 1–3 项（接口定型，第 5 项随之）→ 第 4 项 → 第 6 项。固定流水线的输出应逐字节不变。
