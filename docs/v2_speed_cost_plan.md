# 处理速度与成本：思路（2026-10-04，待新会话研究、对比、实现）

用户要求下一阶段重点优化处理速度和成本。这里只记思路和依据，细的测量、对比、实现放到新会话。原则不变：信息不丢、质量不降；每项改动都要回放核心文档和 30 篇语料，关键内容错误、字、标题、表格分数不变或更好才采用。

## 0. 先测清楚

现在只有每篇的总用时、请求数和总费用，看不出时间和钱花在哪一步。

- 报告（`--report` 的 processing）按步骤记用时、请求数、tokens、费用（扫描引擎、服务模型、Agent 分开）。
- 选一组代表性文档，关掉缓存（`cache.mode: refresh`）各跑一次作为基线：投标文件（DOCX，391 张图，内部语料）、扫描 PDF（ocr_scan_jtg3362）、公式论文（paper_chn02）、表格文档、普通原生 PDF。
- 已有的数（投标文件，不用 Agent，冷缓存 15 分钟、0.13 美元）：图片转正 391 张 5 分 13 秒；图片说明 391 张 3 分 53 秒；图片转写 263 张 5 分 23 秒；用 Agent 时另加约 20 分钟。语料每篇 Agent 30 秒到 7 分钟。

## 1. Agent：最大的时间块

1. **去掉不该有的待办。** 投标文件 530 项待核对里 364 项是"图片里的标题没有层级"（`structure_pending`）：图片转写里的标题本来就写成加粗、不进文档大纲，不该交给 Agent。去掉后这篇的待办少七成。逐类再看其余待办的误报率（`number_unaccounted` 约四分之一是本地读错）。
2. **程序能定的不交 Agent。** 已有先例：GLM 拆开的编号由适配层直接接上（Q151）。逐类看哪些待办有稳定的程序解法。
3. **按价值决定要不要 Agent、看多少。** 数字、缺字、表格这类影响内容的优先；只有低价值待办的文档不起 Agent；按待办数和页数给时间预算。
4. **Agent 的模型和思考强度**：Codex（gpt-6.1-sol）medium 与 low 对比用时与关键内容错误。

## 2. 图片多的文档

1. **本地读数并行。** 转正和读数现在一张一张在 CPU 上做（每张约 0.8 秒、平均读 2 次）；可多进程并行，或用文档方向分类小模型（每张几十毫秒）先定方向、只读一次（要和现在的办法在同一批图上对比）。
2. **服务模型写说明。** 并发 6 是否能提高（看百炼限流）；要转写的内容图其实不需要单独一次说明请求，概述可以和转写结果一起生成或从转写推出；照片、截图可试不思考（effort none）。
3. **扫描引擎转写。** 图片批次是否并行请求（页面已是 2 路）；同一份文档里相同的图（同一张身份证、印章）只读一次。
4. **早跳过。** 装饰图、空白图、小图标在转正、说明、转写之前排除。

## 3. 成本

1. **服务模型是主要花费**（投标文件约 0.13 美元，几乎全是千问写说明）：一张截图约 1200 个图片 token。发送前按需要缩小图片、降低思考强度、相同的图不重复请求，都能省；每项都要看说明质量（公司名、数字写错率）不降。
2. 扫描引擎：GLM 每份文档几分钱；Agent：Codex 包月不另计费，DeepSeek 循环约 7 美分一篇。
3. 报告里给出每篇的费用构成（按服务、按步骤），让用户能看到钱花在哪里。

## 4. 做法

先完成第 0 节的测量和基线，再按"省得多、风险小"排序：第 1.1 节（误报待办）、第 2.1 节（读数并行）、第 2.2 节（内容图不单独说明）大概最先。每项单独提交，附回放结果。
