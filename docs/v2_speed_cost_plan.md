# 处理速度与成本：计划（2026-10-04，待新会话研究、对比、实现）

用户要求下一阶段重点优化处理速度和成本。这里记目标、测试数据、思路和依据；细的测量、对比、实现放到新会话。原则不变：信息不丢、质量不降；每项改动都要回放核心文档和 30 篇语料，关键内容错误、字、标题、表格分数不变或更好才采用。

## 0. 目标与优先级（用户，2026-10-04）

- **速度第一，成本第二。** 一篇文档 20 分钟，比竞品慢得太多；目标是快一个数量级，比如投标文件这一类从 20 多分钟降到两三分钟。
- 时间分两部分，分开分析、分开优化：
  - **流水线**：并行、去掉重复和不必要的工作；
  - **Agent**：通过工具、提示和任务本身的优化，让它更快完成；实在不行就用我们自己的循环（Loop），可以做更自由的定制，成本高一些也可以接受。
- 成本在速度之后看，但每项提速都顺带记下费用的变化。

## 2. 先量清楚

现在只有每篇的总用时、请求数和总费用，看不出时间和钱花在哪一步。

- 报告（`--report` 的 processing）按步骤记用时、请求数、tokens、费用（扫描引擎、服务模型、Agent 分开）；Agent 再细到每次工具调用的用时、模型思考的用时。
- 在速度回归集上关掉缓存（`cache.mode: refresh`）跑一次作基线。
- 已有的数（投标文件，不用 Agent，冷缓存 15 分钟、0.13 美元）：图片转正 391 张 5 分 13 秒；图片说明 391 张 3 分 53 秒；图片转写 263 张 5 分 23 秒；用 Agent 时另加约 20 分钟。语料每篇 Agent 30 秒到 7 分钟。

## 3. 流水线提速

1. **各步之间不必串行。** 现在转正 → 说明 → 转写一步做完再做下一步；各图独立，可以按图流水：一张图转正完就去说明、转写，扫描引擎、服务模型、本地计算同时在跑。
2. **本地计算并行。** 转正和读数现在一张一张在 CPU 上做（每张约 0.8 秒、平均读 2 次）；改多进程并行，或用文档方向分类小模型（每张几十毫秒）先定方向、只读一次（要和现在的办法在同一批图上对比准确率）。
3. **去掉不必要的请求。** 要转写的内容图不需要单独一次说明请求：概述可以和转写一起生成，或从转写推出；同一份文档里相同的图（同一张身份证、同一个印章）只处理一次；装饰图、空白图、小图标在转正、说明、转写之前排除。
4. **并发。** 服务模型并发 6 能否提高（看百炼限流）；扫描引擎的图片批次是否并行请求（页面已是 2 路）、批次多大最快。
5. **剩下的串行步骤**（结构、检查、导出）在中等文档上逐一计时，找出慢的。

## 4. Agent 提速

Agent 是最大的时间块。目标是让它做得少、做得快、能并行。

1. **待办少而准。**
   - 投标文件 530 项待核对里 364 项是"图片里的标题没有层级"（`structure_pending`）：图片转写里的标题本来就写成加粗、不进文档大纲，不该交给 Agent。去掉后这篇的待办少七成。
   - 逐类看其余待办的误报率（`number_unaccounted` 约四分之一是本地读错）；程序能稳定解决的不交 Agent（先例：GLM 拆开的编号由适配层直接接上，Q151）。
   - 按价值决定要不要起 Agent、看多少：数字、缺字、表格这类影响内容的优先；只剩低价值待办的文档不起 Agent。
2. **工具。** 统计每次运行的工具调用次数和每次的用时，找出来回最多的地方：
   - 一次调用就能看到一项待办所需的全部证据（该处的裁图、各份读数、程序的建议改法），不用先读草稿、再看图、再查读数；
   - 一次提交多处修改；
   - 视图只给需要的那一段，图只给该处的裁图。
3. **提示和任务。** 任务说明精简；按待办类型给出处理顺序和判断标准；明确时间预算，低价值的待办可以略过；写清什么情况下直接关闭。
4. **并行。** 待办按页或按类型分成几份，同时起几个 Agent 各做一份（工作区的版本检查已能发现冲突，要看并行修改时怎么合并）。
5. **模型和思考强度。** Codex（gpt-6.1-sol）medium 与 low 对比用时与关键内容错误；简单类型的待办交给更快的模型。
6. **自己的循环（Loop）。** Codex 是黑盒，能改的只有工具和提示。自己的循环可以：并行调用工具、按待办类型换模型、控制上下文和提示缓存、按我们的需要停止。成本高一些，但如果 Codex 的速度到不了目标，就转到自己的循环上来，DeepSeek 在它上面每篇约 7 美分（Q149 的对比：质量比 Codex 稍差，速度相当）。

## 5. 成本（第二优先级）

1. **服务模型是主要花费**（投标文件约 0.13 美元，几乎全是千问写说明）：一张截图约 1200 个图片 token。发送前按需要缩小图片、降低思考强度、相同的图不重复请求，都能省；每项都要看说明质量（公司名、数字写错率）不降。
2. 扫描引擎：GLM 每份文档几分钱；Agent：Codex 包月不另计费，自己的循环按 token 计费。
3. 报告里给出每篇的费用构成（按服务、按步骤）。

## 6. 做法

1. 先做测试数据（第 1 节）和测量（第 2 节），定下速度回归集上的基线。
2. 按"省时多、风险小"排序，大概：Agent 的误报待办（4.1）→ 流水线各步并行与去掉不必要的请求（3.1–3.3）→ Agent 工具和任务（4.2–4.3）→ Agent 并行与模型（4.4–4.6）。
3. 每项单独提交，附速度回归集的用时、费用和质量，以及语料回放结果。
