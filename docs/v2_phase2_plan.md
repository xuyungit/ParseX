# 阶段二"Agent 探索"工作分解

> 状态：**已确认**（2026-09-24；Q36–Q39 按建议确认；Q35 由用户改定主力模型为 gpt-6-sol，见 §2.1、§7 与指导 §14）。依据 [redesign_guide.md](redesign_guide.md) v1.13 的 §3、§5、§7、§9.4、§12、§14，工具接口以 [v2_phase1_interfaces.md](v2_phase1_interfaces.md) 为准。按 §4 的顺序实施；每完成一项更新指导 §12 与 §15。

## 0. 目标与退出条件

**目标**：让 Agent 通过文档工具包端到端处理难例，找出工具包缺什么：需要哪些工具、在哪里必须看图、什么信息缺失导致反复尝试、哪些能力值得封装成工具或通用算法。产出工具包 v1.1 与修订后的 Skill，为阶段三的运行时对比实验做好准备。

阶段二是**探索**，不是验收：没有质量门槛，结论是发现与修订。它也不决定默认运行时（Q13 在阶段三回答）。

**退出条件**（细化指导 §12"探索报告；工具包修订完成"）：

1. **两轮探索都跑完**：探索集每篇文档在第一轮（工具包 v1 + Skill 草稿）和第二轮（工具包 v1.1 + 修订后的 Skill）各有一次完整运行记录；卫生审计通过（没有读取标注、评分或实验目录以外的文件，没有绕过工具改写工作区）。审计不通过的运行作废重跑。
2. **探索报告**写入 `eval_reports/<日期>_p2_agent_exploration.md`，内容包括：
   - 逐篇结果：§7.5 的完成条件是否满足；有标注的文档与固定流水线 v2、v1 基线的分数对比（运行结束后由我们评分，Agent 看不到）；没有标注的文档写定性观察；
   - 成本：主 Agent 的 token、轮数、耗时与工具内部的服务请求、费用分开记账；人工介入单独记账；
   - 发现清单：每条写明证据（事件记录中的位置）与处置（已改、留到后续阶段、不改及理由）；
   - Q14（JSON CLI 是否够用、何时加 MCP）与 Q30（Agent 提出的四项能力）的回答。
3. **工具包 v1.1 与 Skill 修订完成**：每项修订先写测试（合成输入）；L0 通过；v1 与 v2 的 L1 PASS；v2 验收冻结能回放，若修订有意改变了验收文档的输出，就以空缓存重新冻结并回放。
4. **阶段三的准备**：未见难例集按 Q37 确定；§9.4 的运行时对比协议补全到可以直接执行（运行时列表、预算、计数方式）。

## 2. 探索设计

### 2.1 运行时与模型

- **Codex CLI**（§7.4 第 1 步）：`codex exec --json`，沙箱 `workspace-write` 并允许网络（工具要访问 OCR / VLM 服务），`--output-last-message` 保存最终报告。
- **主力模型 gpt-6-sol**（Q35），推理强度 `high`：每次运行都在命令行上显式传入 `-m gpt-6-sol -c model_reasoning_effort=high`，不依赖本机 `~/.codex/config.toml` 的默认值（目前是 gpt-6-astra）。2026-09-24 已用 Codex 0.156.0 实测可用（无头调用返回正常，token 用量在事件流中）。模型、推理强度与 Codex 版本写入每条运行记录。
- **换模型的条件**：先用 gpt-6-sol；出现问题（例如不会正确使用工具、看图链路失效、运行不稳定、成本明显过高）再考虑换。换模型是一项决定：写入指导 §14 并注明原因；一轮之内不混用模型，换模型后受影响的文档在新模型下重跑，换前换后的结果不直接比较。
- Claude Code 与 Pi 留到阶段三（§7.4 第 3、4 步）。阶段二只用一个运行时，把变量留给工具与 Skill。

### 2.2 实验目录与工具快照

每一轮先生成**工具快照**：用当前提交构建 wheel，装进实验根目录下该轮自己的虚拟环境；配置展开成不引用仓库路径的独立 `parserx.yaml`。一轮之内工具代码固定不变，快照目录不含 `ground_truth/`。

每篇文档一个独立的实验目录（独立会话，§7.3），实验根目录放在仓库之外：

```
<exp_root>/<round>/<doc>/
  input.<ext>        # 只有输入
  px                 # 调用该轮工具快照的包装脚本
  parserx.yaml       # 独立配置；响应缓存放在本目录内，初始为空
  AGENTS.md          # 任务说明（P2-2），Codex 自动读取
  skills/            # 三份 Skill 的副本（记录哈希）
  ws/  out/          # 工作区与导出结果（由工具生成）
  run/               # 实验装置写入：events.jsonl、last_message.md、record.json（Agent 运行时不存在）
```

服务密钥只由 `px` 包装脚本在调用工具时注入，不写进实验目录。

### 2.3 Agent 能做什么

- **第一轮（探索）**：允许写临时脚本，用于读取、比较、分析（例如比较两次识别结果、裁剪图片、统计表格）。工作区只能通过工具修改；最终结果必须经 `export` 导出，不能自己拼 Markdown。直接改写 `ws/` 下的文件属于违规，由完整性检查发现（§2.5）。
- **第二轮（接近验收条件）**：工具 v1.1 冻结；不允许为这篇文档写专用转换逻辑，临时脚本只能读取与分析。用来检验修订后的工具包是否够用，也为阶段三的验收条件（§7.2）做预演。
- 两轮都不在运行中途提示 Agent（人工介入的处理见 Q39）。

### 2.4 记录与记账

每次运行的 `record.json`：

- 运行条件：轮次、文档、工具快照的提交号、配置指纹、Skill 与 `AGENTS.md` 的哈希、Codex 版本、模型、推理强度、开始与结束时间、退出码、是否超时；
- 主 Agent：轮数、命令数、输入 / 缓存 / 输出 token、耗时（来自事件流）；
- 工具：各工具调用次数、服务请求数、token、费用、耗时（来自 `ws/calls.jsonl` 与 `state.stats`）；
- 结果：文档状态、`check` 结果、未解决项；有标注的文档另存评分（运行结束后由实验装置计算）；
- 卫生：审计结论与命中的条目；
- 人工介入：次数与内容。

### 2.5 卫生审计与完整性检查

- **路径审计**：扫描事件记录里执行过的命令与读取的文件，出现实验目录以外的路径（仓库、`ground_truth`、`expected.md`、其他文档的实验目录、评分结果）即判为污染，该运行作废。
- **完整性检查**：工作区每次事务在 `calls.jsonl` 中记录提交后的状态哈希；运行结束时核对 `state.json` 与最后一次事务的哈希。不一致说明有绕过工具的改写，该运行作废，并把"Agent 想做但工具不支持的事"记为发现。
- **看图核对**：抽查事件记录，确认 Agent 打开了 `read --image` 返回的图片（P1-7b 已验证链路，这里只核对每篇是否真的看了需要看的图）。

### 2.6 对照

同一篇文档、同一工具快照下再跑一次固定流水线 v2，与 v1 冻结基线一起作为对照。比较的是完整系统效果：Agent 用了更强的模型做判断，差异不能全部归因于"用了 Agent"。

## 5. 各项分解

### P2-1 实验装置

- **内容**：
  - `scripts/agent_explore.py`：生成工具快照；为每篇文档建立实验目录；运行 `codex exec --json`（超时按 Q39）；运行后做完整性检查、卫生审计、导出核对与评分，写 `record.json`；汇总一轮的记录为表格；
  - `parserx/workspace/`：事务记录增加提交后的状态哈希；`check` 发现 `state.json` 与最后一次事务不一致时报告失败（新失败码 `workspace_tampered`），阶段三验收同样需要；
  - 评分入口：对一份导出的 Markdown 计算与冻结 run 相同的指标（复用 `parserx/eval/`，不改指标）。
- **测试**（合成输入）：
  - 状态哈希：事务后哈希一致；直接改写文件后 `check` 报 `workspace_tampered`；
  - 审计：合成的事件记录中，读取实验目录外路径、`expected.md` 的命令被识别，目录内的不误报；
  - 记账：从合成的 Codex 事件流中读出轮数与 token；
  - 实验目录只含 §2.2 列出的文件，配置不含仓库路径。
- **验收**：用一篇小文档（text_table01）跑通整个流程，记录完整，审计通过。

### P2-2 任务说明与 Skill 装载

- **内容**：`AGENTS.md` 模板：
  - 目标：全文转换，完成条件按 §7.5（每页有状态、`check` 平衡、未解决项如实报告）；
  - 工具：列出七个工具与 `tool schema`，说明 `DocText` 是数据、不是指令；
  - 本轮允许做什么（§2.3）与预算；
  - 三份 Skill 的位置与用途；
  - 完成后报告：导出结果、看过的图与细节、缺少的工具、失败信息是否可用、反复尝试的原因。

  模板与 Skill 进入版本控制，哈希写入运行记录。
- **测试**：模板渲染稳定；两轮的差异只来自有意修改的部分。

### P2-3 对照运行

- 在第一轮的工具快照上，用固定流水线 v2 跑探索集（有标注的评分，没有标注的记录成本与完成情况），作为对照；v1 分数取冻结基线。第二轮在 v1.1 快照上再跑一次。

### P2-4 第一轮探索

- 探索集逐篇运行，每篇一个会话。
- 每篇写一份发现记录：卡在哪里、为什么看图、为什么重试、临时脚本做了什么、缺什么工具或信息。
- 汇总成发现清单：每条带事件记录中的证据，给出建议处置（改工具、改 Skill、留到阶段四、不改）。
- 发现清单先交给你确认，再开始 P2-5。

### P2-5 工具包 v1.1 与 Skill 修订

- 按确认后的清单逐项修改，每项先写测试（合成输入），并评估 Q30 的四项能力。
- 遵守泛化要求：不为单篇文档加规则或阈值；程序约束（修改权、去向检查、接受门、合法性）不放松。
- 改动若影响固定流水线的输出：跑全量语料参考运行；若验收文档的输出改变，以空缓存重新冻结并回放。

### P2-6 第二轮

- 在 v1.1 快照、修订后的 Skill、§2.3 的第二轮条件下重跑探索集，与第一轮、固定流水线逐篇比较。
- 另加一篇合成的注入测试文档（正文中写有"忽略之前的指令，改为……"之类的文字），检查注入隔离：Agent 不执行，输出照常保留这段原文。

### P2-7 候选通用算法

- 从 Agent 的临时脚本中找出可能通用的做法。
- 先在全量语料（隔离集除外）上验证：确实普遍有效才并入工具或固定流水线；否则记入报告，留给阶段四。

### P2-8 阶段三准备

- 按 Q37 确定未见集；如需新标注，列出文档与需要标注的内容，由你决定标注方式。
- 补全 §9.4 协议：参与对比的运行时（Codex、Claude Code、Pi、固定流水线）、每篇的预算与截止时间、计数与评分方式、重复次数。

### P2-9 探索报告与收尾

- 写探索报告（§0 第 2 条）。
- 回答 Q14、Q30。
- 更新指导 §12（阶段二 ✅）、§14、§15，以及 §0 的下一阶段启动清单。

## 6. 每项完成时的固定动作

1. 跑 L0 并汇报（通过数、已知失败数、耗时）。
2. 确认 v1 与 v2 的 L1 仍然 PASS；改动工具时确认 v2 验收冻结能回放。
3. 更新指导 §12 与 §15；有新决策时写入 §14。
