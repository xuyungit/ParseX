## 0. 摘要

- **系统**：ParserX 把 PDF、DOCX（含扫描件与图片）转成给大模型用的 Markdown，附 sidecar（块、来源、去向账目）。架构是工作区 + 程序约束 + 四个 Agent 工具 + 混合运行时：固定流水线先做，有待办再交 Agent。指导文档 [redesign_guide.md](redesign_guide.md)。
- **位置**：对标 15 篇，表格、标题、字符、关键内容错误都领先 LlamaParse、MinerU、Datalab、PaddleOCR-VL（§1.2）。落后在只有看页面图像才看得见的东西：公式、上下标、字体画出的字形、画出来的图。
- **最近两轮**：为公式先打 5 个补丁（在 main 上），再按区域整体重做（分支 `content-by-region`，未合并）。规则盘点表明：起作用的是把"看"交给页面读数的部分，以及从 PDF 读出的排版事实；出问题的是看到一处错误后补的条件，它们互相牵制（§1.3、§2）。
- **提议**：按人整理文档的方式分工（§3）。服务模型看页面图，写出这一页的块序列；文字层逐行编号、带着排版事实作为"可复制的原文"一起交给它。服务模型对能复制的内容只引用行号，由程序放入原文；复制不了的才自己写。**输出必须把文字层的每一行完整分配一次**：复制、被重写块替换、或带理由放到一边。程序只保证账目与格式正确，并把各种比对作为证据与信号；**最终判断归 Agent**，程序不用逐字相同一类的机械规则限制它，控制 Agent 靠准确的 Skill、提示词、证据要求与审计记录。
- **先探针，再铺开**：先在十来个难页上验证"完整分配"这个做法与几个服务模型的能力，过关再做完整对比，最后比较 Agent 自己看图与委托服务模型看图（§6）。实验前不加规则，分支不合并。

## 2. 诊断

1. **界线不在"几何还是视觉"，而在"读出排版事实"还是"看到错误后补的条件"。** 字号、基线、字体、无映射字形、位置是 PDF 里测得出的事实，读出来交给后续步骤是对的（上下标实测有效）。出问题的是为一处错误补的条件，以及让程序按样子猜含义（这是下标吗、是标题吗、两段要接上吗、哪份读数更好）。指导 Q56 与 2026-09-23 的规则分类早已写明后者只能作证据；实施时在对标分数的压力下一次次破例。（第一版把界线画在"几何"上，说过头了，照此会把排版事实一起丢掉。）
2. **规则互相依赖，局部修正变成全局牵制。**
3. **评测体系本身可用，但有盲点**：规范化把上下标折叠，逐篇看图量一大就漏。要补的是看得见退步的检查，不是换评测。
4. **上一版计划方向对，落地又回到规则里**："结构来自页面图像"被实施成程序里的区域几何与比例常数。分支上的简化方案（`docs/v2_content_simplification.md`）三条中，"页面几何只算一次"撤回；"字形可信度定一次""以文字层为底"在本文的完整分配里有更简单的实现，不单独做。
5. **不是问题的部分**：工作区、去向账目、四个工具、混合运行时、表格网格、DOCX 读取。全部代码约 2.6 万行，与多来源融合相关的内容获取部分约 4 千行；本文的改动限于这一部分。

## 3. 设计：拟人的分工

### 3.1 分工与原则

| 人怎么做 | 系统里由谁做 |
|---|---|
| **看**：一眼看出版面、阅读顺序、标题、公式、图 | 服务模型看页面图，写出这一页的块序列 |
| **能复制的就复制**：正文从 PDF 复制，字是准的；乱码、公式照着页面重打 | 文字层逐行编号、带排版事实交给服务模型；能复制的只引用行号，由程序放入原文；复制不了的才自己写 |
| **核对**：重打的地方数字对不对、有没有漏段 | 程序做比对，结果是证据与信号，决定固定流水线的保守默认值 |
| **拿不准就凑近看、自己拿主意** | Agent 看图，结合证据作最终判断 |

**原则（用户，2026-09-29）**：最终判断归 Agent，要相信它的能力；程序不能用逐字相同、字符相同这类机械规则限制它。要控制的是 Agent 的做法：Skill 与提示词写准确、写清楚，每个决定带证据与理由，程序记下并在摘要里列出，用过程指标衡量。

程序的规则因此分三层：

| 层 | 内容 | 作用 |
|---|---|---|
| **不变量**（硬） | 文字层每一行恰好分配一次；引用的行号、块号存在；LaTeX 配平；输出里没有无映射的码点（私用区、U+FFFD） | 只保证账目与格式正确，不涉及内容取舍。违反时机械处理（没分配的行按位置补回并列待办），不作判断 |
| **比对**（证据） | 重写块与被替换行的数字、字母、数学之外的文字；输出是否在页面上看得到（本地读数）；与引擎读数是否一致 | 产生待办信号与证据；决定没有 Agent 时的保守默认值 |
| **Agent 决定** | 采用哪份候选、自己改写、保留文字层、重读、关闭待办 | 凭看图的证据，可以作出与比对结果不同的决定（包括与文字层数字不同的写法），程序记录并列出 |

### 3.2 输入（每个分流页）

- 页面图（现有渲染）。
- 文字层逐行：行号、文字、阅读顺序；**排版事实**随行给出——按字号与基线读出的上下标（保守：只用字号与基线，不用"小一号就算"这类补的条件）、加粗、无映射字形标记（`⟨?⟩`）。
- 有公式的文档再给扫描引擎的读数条目（带框与 LaTeX）：实测公式相似度最好，也可作重写块的锚点。
- 检测器区域只作提示。

### 3.3 输出契约：完整分配

JSON（结构化输出）的块序列，按阅读顺序。每块给出类型（正文、标题、列表、表格、行间公式、图、图注、脚注、其他），以及内容来源之一：

- `copy`：引用行号区间，程序把原文（含排版事实）放入；
- `write` + `replaces`：服务模型自己写的文字，声明它替换哪些行；行间公式可声明取自哪个引擎条目；
- `table`：引用行号区间，网格由现有抽取给出；
- `aside` + 理由：页眉页脚、图内文字等放到一边的行。

每一行恰好出现在一处。由此：漏段和重复成为机械检查；来源锚点与账目靠构造就有；人工只需看 `write` 块。

### 3.4 比对与默认值

- **数字**：`write` 块的数字与它替换的行（加页面读数）相比。
- **字母、数学之外的文字**：同样相比；需要"LaTeX 的字符表"的逐字母比较只作信号，不作门。
- **页面上看得到**：输出的文字在本地读数里是否有。
- **没有 Agent 时的默认值**（保守，全部列待办）：正文类 `write` 与被替换行的数字不一致时，保留被替换行的原文，`write` 作为候选附在待办里；行间公式不一致时，先取数字一致的引擎读数，都不一致就输出不一致最少的候选并标为降级（与 [v2_content_plan.md](v2_content_plan.md) §9 的决定一致：行间公式不退回文字层碎片）。

### 3.5 Agent 的最终判断与控制

- 待办指向块；`view_source` 看这一块的图；待办里并列候选（服务模型写的、引擎读的、文字层原文）与比对结果。
- Agent 可以：采用任一候选、用 `replace_text` 改写、区域重读后 `adopt`、保留文字层、关闭待办。现有工具够用，不加公式专用操作。
- 与文字层数字不同的写法，Agent 凭看图证据可以采用；程序记下证据与理由，摘要列出"Agent 改动了原生数字的地方"。**这改变了指导 §11.5 的一条正确性要求**（原生数字只在本地读数显示新值时才能改），待用户确认（§10）。
- 控制手段：Skill 写清每类待办看什么、能做什么、证据怎么引用；提示词给出候选与比对的呈现方式；过程指标（改对、改错、无关）逐条对照标注判定。

### 3.6 表格、标题、图

- **表格**：服务模型只标出范围、引用行，网格仍由现有抽取给出（现路径领先：0.942 对 LlamaParse 0.693）。
- **标题**：服务模型给的块类型只作标题步骤的证据；层级由现有的全文标题步骤与 Agent 定（服务模型逐页看不到全文层级）。
- **图**：服务模型标出图的范围，图内文字的行放在 `aside`（理由：图内文字），图从页面裁出，走现有的描述。

### 3.7 分流

- 有公式证据的文档整篇送（消融已证明只送标出的页会漏）。
- 其余文档只送有证据的页：检测器看到图而页面没放图、有无映射字形、本地识别与文字层不一致（沿用已有的待核对信号，不设新阈值）。
- 普通页里的上下标与脚注角标，文字层与本地识别会一致地拉平，不会被分流；靠 §3.2 的排版事实在不分流的页上也输出，兜底。

### 3.8 与来源无关的接口

"可复制原文 + 页面图 → 完整分配"不限于原生 PDF：扫描页可用引擎条目作可复制原文（不精确，数字比对的分量相应降低）；推迟的 Word 矢量图（B 线）可用 LibreOffice 渲染的页面图配 OOXML 段落。本轮只做原生 PDF。

## 5. 服务模型与 Agent 用的模型

两种角色分开（Q40）：**服务模型**（看页面写块序列、编辑、回答 Agent 的看图问题）与 **Agent**。本实验比较的是服务模型；Agent 默认 Codex。

| 模型 | 用途 | 接口与参数（2026-09-28 探测） | 价格（美元/百万 token：输入、缓存、输出） |
|---|---|---|---|
| gpt-6-luna | 服务模型，现默认 | json_schema 遵守；不接受 temperature；强度除 minimal 外都接受 | 0.10、0.01、0.50 |
| gpt-6-sol | 服务模型的上限检查；Codex 的 Agent 模型 | Responses 接口；按 API 计费（Codex 包月另算） | — |

### 5.1 结构化输出：参数配置，不写适配层

完整分配要求服务模型输出合乎 schema 的 JSON，四个模型在这一点上不同，要决定是为 DeepSeek、GLM 各写适配层，还是参数配置就够。

**事实**：

- DeepSeek 官方 [JSON mode](https://api-docs.deepseek.com/zh-cn/guides/json_mode)：`response_format: {"type": "json_object"}`；提示里必须有 "json" 字样，并给出希望输出的 JSON 样例；有概率返回空的 content；`max_tokens` 要够，否则 JSON 被截断。文档没有 json_schema。
- GLM 官方 [结构化输出](https://docs.bigmodel.cn/cn/guide/capabilities/struct-output)：`response_format: {"type": "json_object"}`；在系统消息里定义期望的 JSON 结构，可以用描述，也可以把 JSON Schema 写进提示；建议程序再校验。文档没有 json_schema 类型。
- 我们 2026-09-28 的探测与此一致：DeepSeek 拒绝 json_schema；GLM 接受 json_schema 却不遵守（返回带围栏的 JSON）。两家都是 OpenAI 兼容的 Chat 接口，JSON mode 的请求形状与 OpenAI 的 `json_object` 相同。
- 现有服务层已经按条目参数处理：`models.<名字>.structured_output` 定它遵守的最强方式（这两家是 `json_object`）；弱于 json_schema 时自动把 schema 写进提示（Q105，f048430）；带围栏的 JSON 会剥掉；`min_output_tokens` 抬高输出下限（DeepSeek 8192）；`efforts` 定可发的推理强度；`api_style` 选 Chat 或 Responses。

**决定（建议）**：参数配置，不写适配层。**判断标准**：只有请求或返回的形状不同（换了一种接口、字段结构不同）才写适配层；同一种接口上的能力差异用 `models` 条目的参数表达。DeepSeek、GLM 属于后者。

**要补的都是与提供方无关的通用做法**，写在服务层或任务提示里，对四个模型一样：

1. 完整分配的提示同时给 schema 和一个简短的 JSON 样例（DeepSeek 要样例；对其他模型无害）。
2. 程序对返回做三级校验：能解析、合 schema、满足不变量（§3.1）。不过时带着校验错误重问一次；仍不过，按不变量的机械处理退回（§3.1）并列待办。
3. 空答复当作一次失败重试（DeepSeek 文档明言会出现；现有调度层是否已把空答复当失败，实施时先确认）。
4. schema 放在系统消息还是用户消息，只在 P0 测出某个模型的格式合法率明显偏低时再试；需要时加一个条目参数，不写适配层。

P0 为每个服务模型量格式合法率（能解析、合 schema、满足不变量三级），以此验证这个决定。
