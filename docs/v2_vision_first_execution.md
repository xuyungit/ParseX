## 3. 执行设计（在共同计划 §3 上的补充）

### 3.1 输入

- 页面图（现有渲染与旋转约定，不另起坐标系）。
- 文字层：行号、行内 span 的**原字符**、框、字号、字体、基线、映射异常（私用区、U+FFFD、Symbol 字体部件）。
- **候选**（单独一栏，模型可以接受或纠正）：按字号与基线得出的上下标候选；不给"小一号就算"一类补的条件。
- 有公式的文档：扫描引擎条目（框与 LaTeX）。检测器区域只作提示。

### 3.2 输出契约

- 文字层每一行恰好一个去处：`copy`、被 `write` 声明替换、`table`、`aside`（带理由）。
- **视觉发现的内容**另列：没有文字行锚点的块（画出来的图、只画不写的符号、公式里文字层没有的部分）以页面区域、引擎条目或图片为来源登记，不为"恰好一次"丢掉。
- `aside` 与图内文字要留下最终去处：放进哪张图、哪段说明，或明确排除（页眉页脚），可以核对。

### 3.3 P0 的核对与指标

- **整页人工核对**（对原件，不只对标注）：`copy`、`write`、`aside`、表格、图、脚注、阅读顺序都看。
- 分开报告：结构化输出（首次合法、schema 合法、重试后合法、机械修复、最终失败；截断、空回复、超时单列）；输入分配合法率（首次与补回分开）；原件内容覆盖率；转写正确率；具体的误改与漏项；每页 token、用时、费用。
- 失败分类：服务模型能力不足、图片不可读、契约不合适、分配错误、原文证据错误、评测误判。不以追加文档特例解决。

### 3.4 Agent 的权限与记录（R3 的实现清单）

- 内容修改的记录：原值、新值、来源区域、所用证据编号、理由、版本（Decision 与修改历史已有大部分字段，补齐缺的）。
- 要改的实现：`content/select.correct`（原生数字只在本地读数显示新值时才能改）→ 有看图证据即可，记录并在摘要列出"Agent 改动了原生数字的地方"；`tools/edit._adopt_region` 的原生数字与 90% 字符召回 → 同样改为证据与记录，召回作为信号给 Agent；`insert_text` 的独立读数门保留为信号。
- 不放宽：引用的块、证据、页存在；来源定位；修改范围合法；历史留存；`unadopt` 可撤回。
- Skill（`skills/transcription.md`）与任务说明同步改写：每类待办看什么、能做什么、证据怎么引用、看不清就留作未解决。
- 测试：每个放宽的门各有"有证据可改、无证据不可改、记录完整"的用例。

- C0.6 的经济性目标沿用共同计划的每个分流页 $0.005；质量过关而超预算记为"质量可行、经济性未达标"。

### 4.1 评测器先修（任何比较之前）

1. 新检查：正负号、单位、上下标（不经 NFKC）、数值与对象或单元格的归属、公式结构（记法归一后的相似度已有）、整块遗漏。
2. 每类检查用通用的反例类别写测试（符号翻转、上下标互换、归属交换、整段缺失），不写针对具体字符串的特例。
3. 评测器定版后，M、R、L 等所有已有输出用同一版本重算；以后评测器或标注再变，所有臂一起重算。

### 4.2 同口径基线表

固定每个臂的冻结 run、代码提交、标注哈希、评测器版本、输入哈希，重新生成对标表：逐文档、逐页；费用分实付、标价估算、未知；回放用时单列。对标报告里 ParserX 两列取自 M 还是 R 要明确分开，不混用。

## 6. 两组协作规则

- **独立**：本方在冻结自己的候选之前，不读取另一团队 worktree 里的实现与运行结果；计划与审核类文件由用户转交。对方的执行计划也写明了同样的规则。
- **共享**：共同计划、C0、输入原件、评测器版本、盲测清单（冻结后）。
- **冻结交付包**（C0.7）：提交或补丁、依赖锁定、运行命令；Skill、提示词、配置的版本与哈希；输入、标注、评测器哈希；全部 Markdown、资产、来源对应、未解决项、原始轨迹与错误输出；逐文档逐次指标与人工核对记录；费用与时间分层；已知失败与不能支持的结论。
- **互审**：以"文档—页或区域—现象"为单位，先对原件判错，再看实现原因；不以总分排序代替。
- **吸收**：每项写清来源、解决的问题、代价与验证；形成新候选后在回归集与新的留出样本上重跑，不拼各版本的最好分数。
