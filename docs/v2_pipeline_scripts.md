# 流水线从文字层判断上下标（第一步）

2026-10-01。代码在 vision-first 工作区的新分支 `pipeline-scripts`（从 `6700663` 开出），**未提交**。

## 1. 做了什么

原生 PDF 的文字层把上下标存成"字号更小、基线抬高或压低"的字，流水线以前只读字符，k₁ 读成"k1"，m² 读成"m 2"。现在：

- **判断**：新模块 `parserx/content/scripts.py`，在整页的行上判断每个字是不是上下标、挂在哪个底字上。几何沿用 V 输入脚本里量过的"候选第 2 版"，有 4 个排版常数（缩小比例 0.85、基线偏移 0.12、行偏差 0.6、贴靠距离 0.5），本次没有新增常数。
- **正文**：块的文字不变，只加上 `sub` / `sup` 标记，和粗体一样，由渲染写出。标记带着"前一个字"一起定位，免得落到前面别的"1"上。标题也写出上下标。
- **表格**：格子文字在提取时直接写成上下标。上下标字符取它底字的竖直位置，免得 PyMuPDF 拼格子时把它分到另一行（以前输出里的"β 1"就是这样来的）。
- **写法**：和 V 的 `_unicode_scripts` 一样。每个字都有 Unicode 形式就写 Unicode（k₁、m²、10⁻⁴），否则写 LaTeX（`$_{sd}$`、`$^{[1]}$`）。

改动的文件：
- `parserx/content/scripts.py`（新）、`tests/test_scripts.py`（新，18 个测试）；
- `parserx/content/pdf_native.py`、`parserx/render/emphasis.py`、`parserx/render/markdown.py`、`parserx/ir/observation.py`（`Mark` 加 `sub`/`sup` 和 `before`）；
- `parserx/content/text_audit.py`（"读不出的字符"改为公开函数供复用）。

这几个文件在本方 vision-first、对方 `ae672aa` 和 main 上原本完全相同，两边都能直接合入。

## 2. 比 V 的候选第 2 版多改的五处

都是对照原件查出的测量问题，不针对某篇文档。

| 问题 | 原件里的现象 | 改法 |
|---|---|---|
| 中文字体的名义字号不可比 | 方正排版的 PDF 里，中文字体名义字号 21.25，字框也按 21.25 算，但相邻汉字起点只隔 10.48；正文西文字母 10.29。中文逗号、"和""等"因此显得"更大"，旁边的字母被当成它们的上下标 | 用本页相邻两个汉字的间距量出该字体的实际字身，按比例更正这个字体所有字的字号；没有连续汉字的字体不动 |
| 左括号作底字 | 公式里放大的"("（14.55）旁边，正常大小的 δ、"＝"被判成上标 | 左括号类（Unicode 类别 Ps）不作底字。排版上没有挂在左括号上的上下标 |
| 放大的运算符作底字 | "∑"（14.75）后面正文大小的 δ、Δ、p 被判成上标 | 上下标还要小于本行正文：取同一行里字母和数字的最大字号，同样按 0.85 比例 |
| 隔栏"贴靠" | 双栏页里，左栏行尾的"．"落在"值"的字框里，右栏相距 97 点的英文参考文献被当成"值"的上标 | 从底字到上下标，不同文字层行之间的每一处空隙都不超过 0.5 个字身；同一行内的字由文字层自己连在一起（撇号 z₁′ − z₂′ 不受影响） |
| 行的主字号按"字体+字号"计票 | "(2EIδ₁₁)⁻¹"一行里，字母、希腊字母、数字分属三种字体，下标"₁₁"反而得票最多，主基线落到下标上 | 判断上下标时只按字号计票（字母和数字），平票取较大的 |

另外：只由读不出的字形（私用区、U+FFFD）组成的一段不写成上下标，因为读不出它是什么。

## 7. 分工定下之后的三处修改

用户同意按内容分工：
- **公式**一律走看图（公式工具：扫描引擎读图，读法守恒就采用，否则服务模型对着截图再写一遍，仍定不下来的留 `formula_candidate` 给 Agent）；
- **普通文字里的上下标**，谁读字符谁顺带读位置：扫描页由扫描引擎读，Word 读文件属性，文字版 PDF 用几何判断；
- **拿不准的**保持平写，不建待办。

据此改了三处：

1. **几何判断不碰行间公式区**（检测器标签 `display_formula`）。行内公式仍保留几何判断，因为公式工具采用自己的读法时会整段替换，几何结果只在它没读或没采用时起作用。
2. **Word 的上下标**：读 `w:vertAlign`，包括直接设置的和字符样式里设置的。脚注引用（会写成 `[^n]`）除外。中文下标写成 `$_{\text{升}}$`。
3. **拿不准的不写**：左边找不到底字时，只有右边是字母或数字才算前置上下标（¹³C、脚注"∗Corresponding"）。前提是底字本身不是上下标，引用"[1]"里的数字照旧。

### 8.2 做法（`parserx/content/glyphs.py`，接在提取文字层时）

吸收了对方 `tools/glyphs.py` 的三条：
- 按"字体 + 字形编号 + 码"认定同一个字形；
- 图像读法要和左右已知的字对上；
- 至少两行不同的文字给出同一个字，且没有一行给出别的字。

改动有三处：
- **读法**：用流水线已有的本地识读器（rapidocr，CPU，不花钱、不调服务）读这一行的截图，提取保持离线；
- **核对范围**：只核对字形左右各 4 个字，至少一个可读，不要求整行一致，因为本地识读器读长行时常在别处出错；
- **替换时机**：提取时就替换，上下标判断、表格格子、公式工具的守恒核对用的都是改好的字。每个块记一条决定，旁注里有替换记录。

不认读的情况：
- 行间公式区、图片区里的字形：公式交给公式工具，图里的字由图片承载；
- 文字层被判为不可用、整页交给扫描引擎的页。

整行没有一个可读字的：
- 在图片区里，或原图上那里看不到文字（装饰线），就不作为正文输出，块记为排除，原文留在旁注；
- 在行间公式区里的保留，交给公式工具；
- 原图上看得到文字的保留，照旧以 `text_suspicious` 待办交给 Agent。

### 8.3 中途发现并改正的问题

- **排除了公式区里的行**：打乱了公式工具的组段和守恒核对，公式退回原文。现已改为公式区一律不动。
- **整行截图、每种读满 8 行太慢**：paper_chn01 从 4 秒涨到 83 秒。改为同一行只读一次、两行一致就停、跳过公式区和图片区、跳过整页交扫描引擎的页之后，认读本身约 2 秒（含加载识读模型）。
- **回放的伪回归**：文字层改了字之后，公式工具发给服务模型的请求内容随之改变，只读缓存里没有，于是退回原文。为此另复制一份缓存，设成"命中就回放、缺的才请求"再跑。实际只多请求了 3 次 gpt-6-luna：paper_chn01 两次 0.0014 美元，paper_chn02 一次 0.0007 美元。

## 9. 矢量图（第三步，未提交）

### 9.1 问题

PDF 里用线条画的图（流程图、示意图、尺寸图）页面上没有位图，流水线只取位图，所以这些图整张丢失：
- 图里的标签成了正文里零散的段落；
- 标签读不出的，就成了"������"乱码。

30 篇里有两篇：paper01 的图 2–9（8 张），paper_chn02 的图 3。本方只跑流水线、V、对方流水线三份输出都没有这些图。

### 9.2 做法（`pdf_native._vector_figures`）

**判定**，要两个独立依据同时成立：
- 版面检测器在文字版页面上标出"图片"或"图表"；
- 那里画有不压在任何位图上的线条。

**不当成矢量图的**：
- 只有文字、没有线条的区域（paper01 图 1 的代码框），仍按正文处理，代码不会丢；
- 照片外框、画在照片上的标注线，中心压在位图上，仍按位图处理。

**截图**：区域按里面的线条和文字行适当扩大，免得切掉边缘的标签，再从页面截成图片，资源角色记为 render。图里夹着的小位图（paper_chn02 图 3 里两个 5×1 点的箭头碎片）属于这张图，不再单独输出。图片块记一条决定，写明线条数和吸收的位图数。

**图里的文字**：
- 文字层的行用"包含"关系挂到图上，渲染时作为图片文字写在图下，不进正文；
- 整行读不出的照旧排除。

**后续处理**：服务模型照常给新图写图片说明。因为资源角色是 render，扫描引擎不会再转录一遍，图里的字不会重复。

## 10. 扫描件公式的第二份读法（第四步，未提交）

### 10.1 做法（`parserx/tools/second_reading.py`，流水线在图片转录之后的一步）

- **选块**：扫描引擎读出、带数学的块，也就是独立公式和含行内公式的段落；只选扫描页上的，或扫描引擎从图片里转录出来的。文字版公式页上那些已和文字层核对过守恒的不选。
- **第二份读法**：截这一块的图，交给服务模型照图逐字抄写（gpt-6-luna），不给它看扫描引擎的读法。
  - 页面上的块从页面截；
  - 图片里转录出的块从那张图片里按像素位置裁。
- **比较**：比两份读法的字母和数字。LaTeX 按字符读，Unicode 上标折成普通数字，区分大小写。
  - 服务模型只看到这一块的前半段时（扫描引擎会把跨栏的段落整段读进第一块），它读出的若逐字是扫描引擎读法里连续的一段，就算一致。
- **结果**：一致就照旧；不一致就把第二份读法存在块上作证据，生成 `second_reading` 待办交给 Agent。输出本身不改。
- **配置**：开关是 `runtime.second_reading`，默认开。

### 11.2 改字守卫原来的问题

旧规则（`as_printed`）：Agent 把某些字写成别的字时，看这个块的几份独立读法——文字层、识别引擎、本页的本地读法。至少两份和初稿一致、又没有一份显示改法，就拒绝。它有两个毛病：
- **看不见上下标位置的改动**：No 改成 N_o 不算改动；
- **识别引擎一起读错时，当成了两份独立证据**：μL 被两个引擎都读成 pL，正确的改动反被拒掉。

### 11.3 做法

**上下标位置也算改动**：
- 比较字符时，同时看它写在哪一层：正文、下标或上标（`content/latex.placed`）；
- LaTeX 的 `_` `^`、Unicode 上下标字符、HTML 的 `<sub>` `<sup>` 三种写法算一样。

**改字时请两个读者独立重读**：
- 什么时候重读：Agent 的改动把字母、数字换成别的，或把字挪进、挪出上下标；
- 怎么重读：编辑工具在应用改动之前，截下这些块的图，交给配置的两个读者各自再读；不给初稿，也不告诉它们 Agent 的说法；所有块的请求同时发出；
- 重读的结果记入块的观察（`recheck`），改动采用与否都保留，再改同一块就不再请求；
- 扫描块已有第二份读法（§10）的，直接用那两份，不再请求。

**怎么判**（`content/select._read_alone`），逐处看每一处改动：
- **放行**：每份重读，在它读到的每一处，都显示 Agent 的改法；
- **保留初稿**：有一份重读在某处显示初稿，或读成了第三种写法；理由里写明是哪个读者；
- **退回旧规则**：所有重读都没读到改动的位置（截图没覆盖到，例如块的位置只框住了公式编号）；
- **文字层优先**：文字层映射了每个字形时，它就是原件印的字。文字层显示初稿的字，就保留初稿，读者怎么读都一样；文字层不区分上下标，位置由读者判断。

**两处写法上的补充**：
- 公式块的文字是不带 `$` 的 LaTeX，整体按数学读；自己带定界符的，按定界符读；
- TeX 用无点的 ı 加一个单独的重音字形拼出 í（`Mart´ın`）。这样的重音字形和 ı 现在按 i 算，不再当作改字。

## 12. 整段写出公式段（C）

### 12.1 问题

公式工具（Q70）保留文字层、列成 `formula_candidate` 待办时，有两种情况 Agent 用 `replace_text` 改不了：
- 一段被文字层切成几块（一个公式切成好几块）；
- 公式结构整体要重写。

`replace_text` 只能在一块里替换一个片段。

### 12.2 做法（`edit_draft` 的新操作 `transcribe_passage`，吸收对方的同名操作）

**写法**：Agent 看过整段原件后，把这一段的正文、公式和编号照图完整写出，公式用 LaTeX。

**程序核对四条，不过就拒绝并说明**：
- **证据看得到整段**：看这一块（看待办的块就看到整段）、它所在的整页，或包住整段的区域；
- **一个字不少**：和扫描引擎读法、编辑版本用同一条规则（`formulas._lost`），文字层的每个字母和数字都要写出；只有文字层有、别的读法都没有的字形不算，那是映射错了的字形；
- **多写的字有读法看得到**：多写的每个字母或数字，要么在扫描引擎的读法里，要么在本地读法里，否则就是 Agent 自己加的（比如凭意思补的 σ）；
- **LaTeX 能排版**：`$`、`$$` 成对，花括号成对，环境和 `\left`/`\right` 都闭合（`content/latex.problems`）。

**采用**：
- 和读法被采用时一样：新块替换原来的块，原来的块保留为重复块；
- `unadopt` 能撤回：原来的块恢复，待办重新出现。

**和对方做法的区别**：
- 对方要 Agent 列出全部成员块，本方由程序按段落找出；
- 对方要求字母保留 90%，本方用公式工具同一条"一个不少"的规则，并加上多写的字要有读法看得到。

- 正文照印的写，存疑记录永远不改正文。

**两个来源**：
- **Agent 主动记**：`edit_draft` 的新操作 `doubt`。印的写法必须是这一块里的片段，证据要看得到这一块；
- **被拒的改动自动记**：Agent 的改字被拒，而且拒绝的理由是页面印的就是初稿时（文字层显示初稿的字，或重读读到初稿，或旧规则下两份读法与初稿一致），程序把"初稿写法 → Agent 的写法"记为存疑。Agent 看到了一个"错"，而页面确实这么印，这正是疑似原件错误。
  - 这一次修改整个回滚时，这类记录也保留，重复尝试不重复记；
  - 重读读成第三种写法时不记，拒绝理由里提示 Agent，确信原件有错就自己用 `doubt` 记。

**交付**：
- 摘要文件（`<名>.json`）新增 `doubts` 列表：块、页、印的写法、疑为、理由、是否来自被拒的改动；
- `read_draft` 的 notes 视图列出这些记录，摘要视图计数。

**提示**：转录技能和 Agent 任务说明改为：认为原件有错，用 `doubt` 记下，正文不改；表格算术本来不一致的，也用 `doubt` 记。语义只用来认清看不清的字，LaTeX 只加结构不增删字符。

## 14. 代码行不论角色都保留（E）

### 14.1 问题

**第二轮**：对方的 Agent 把含命令行的编号步骤设成列表项。这个判断合理，但渲染器按列表渲染时，把块里的等宽代码行接成了一段（text_code_block，两次运行都是）。

**本方**：有同样的缺口。渲染器只在块的角色是正文时，才把等宽字体的文字当作代码块（`code_face` 要求 `BlockKind.TEXT`）。Agent 把代码块设成列表、图表题、脚注或"其他"，它的命令就会被接成一段。

### 14.2 做法

- **渲染**：用等宽字体、且不是正文字体的文字，在正文、列表、图表题、脚注、其他这几种角色下，都按代码块输出，保留每一行。代码是排版事实，角色是 Agent 的结构判断，两者互不改写。
- **标题除外**：标题保持一行。把多行代码设成标题，这样的错没见过，不加规则。
- **告知 Agent**：`set_role` 的说明里写明这一点。

### 14.3 结果

- 30 篇回放：输出与此前逐字相同（流水线自己不会把代码设成别的角色）；
- 两篇代码文档在流水线里本来就对：text_code_block 的标注代码行 11 行里只有 1 行不同（fstab 那行被拆在正文和代码之间）；text_pic02 的 16 行里有 3 行不同（原件里换了行的超长表格边线）。这两处都是原件排版造成的，不改；
- 合并代码与正文（`join`）也会丢行，但这同样是没见过的错，不加规则。

## 16. 修 §15.4：排除不再让内容失去出处（main 上的分支 `exclude-keeps-content`）

## 20. DeepSeek（deepseek-flash）总评

### 20.1 用在哪里（当前配置）

- **流水线的第二份读法**（§10）：扫描页上、或扫描引擎转录的图片里带数学的块，luna（low）和 DeepSeek（medium）同时各自照图再读；两份读法都和扫描引擎不同、而且错在同一个字上，才列为待办，交给 Agent 看图定夺。
- **Agent 改字时的重读**（§11、§18）：只用 DeepSeek（`tools.recheck_readers`），不给它初稿；它在改动处显示 Agent 的改法，改动才放行。
- **不用的地方**：其他服务模型工作（图片描述、公式编辑、表格复核、回答 Agent 的提问）仍是 luna；Agent 本身是 gpt-6.1-sol。

### 20.2 质量（实测，样本都只有几十处，只能看方向）

| 测什么 | DeepSeek | luna | 来源 |
|---|---|---|---|
| 抓扫描引擎读错（51 块中 9 处已核实） | 8 | 9 | §10.4 |
| 误报（40 块读对的） | **5** | 9 | §10.4 |
| 原件印的"错"照印的写（10 处陷阱） | **6** | 3 | §11.5 |

| 作为改字裁判：只挪上下标位置的改动（第二轮 12 处） | 11 | — | §18 |

**速度和费用**：

### 20.3 毛病

- **按意思"纠正"原件**：No→N₀、r→γ、李生→孪生、palladium(o)→(0)。所有测过的模型都有，DeepSeek 比 luna 少（照印 6/10 对 3/10），但不免疫。它和 Agent 往往错在同一方向，所以拦不住这类错。
- **模糊字形上不稳定**：同一张截图，两次请求分别读成 H 和 μ（温度为 0 也一样）。

### 20.4 结论：什么时候用

- **适合**：只看图、逐字抄写或核对的独立读者，也就是第二份读法和改字重读。测过的模型里，它做裁判最准、误报最少、最快，费用也低。

- **没评估过**：作为通用服务模型（图片描述、公式编辑、表格复核、回答提问）。这些仍用 luna，要换得单独评测。
- **以后复核**：有更多真实改字数据时，再核一次这些数字。
