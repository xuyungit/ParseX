## 0. 目标与退出条件

**目标**：做成可以交给用户用的版本：

- `parserx parse` 默认走 v2 混合方案，并在控制台清楚地显示进度与结果；
- 补齐典型文档仍会碰到的能力缺口，让混合方案在全语料上整体不低于 v1。

**退出条件**：

1. **可用**：`parserx parse <文件>` 不加参数就走混合方案，交互按 P4-2 的设计。以下几种情况都有测试：
   - Codex 未安装或未登录（只用固定流水线，并说明原因）；
   - Agent 失败、超时，或绕过工具改动了工作区（回退到固定流水线的结果）；
   - Ctrl-C 中断后再次运行，从中断处继续；
   - 非终端输出与 `--json`。
2. **全语料参考运行**（L2，混合方案；只有被分流的文档调用 Agent）：
   - 信息类指标（char_f1、表格 F1）逐篇不低于 v1 超过容差 0.005，标注写法造成的逐条列明；
   - 标题（heading_f1、角色 F1）的平均值不低于 v1；
   - "有信息的图片被丢弃"为 0。
3. 指导 §12、§14、§15 与 §0.2 更新；报告写入 `eval_reports/`。

## 2. 各项设计

### 2.1 P4-1 混合运行时作为产品默认（Q13、Q57、Q61）

**流程**：

1. `workspace init`；
2. 标准处理（`process`）；
3. 导出固定流水线的结果（保留一份，回退时用）；
4. 按分流规则判断：`review.open > 0` 或状态不是 complete 就交给 Agent，否则直接输出；
5. Agent 在同一工作区上处理：看图、修改、关闭已核对的提示；
6. 核对工作区完整性（`verify_workspace`），通过后重新导出，写入文档摘要。

**回退**：以下情况一律输出第 3 步的结果，在摘要与控制台说明原因，并保留仍未处理的待核对项：

- Codex 未安装或未登录；
- Agent 失败、超时（Q39：100 页以下 30 分钟，否则 90 分钟）；
- 完整性不通过（有绕过工具的改动）。

**配置**：

- `runtime.mode: hybrid | fixed`，默认 hybrid；
- `runtime.agent`：`engine: codex`、`model: gpt-6-sol`、`effort: medium`，截止时间按 Q39；
- `pipeline` 默认改为 `v2`（Q61）。v1 保留 `--pipeline v1` 入口，到阶段五删除。

**Agent 运行时接口**：`AgentRuntime` 协议有 `available() -> (bool, 原因)` 与 `run(work_dir, deadline, on_event) -> AgentOutcome`。

- Codex 实现沿用 `runtimes/codex.py` 的事件解析，以及实验装置的任务说明渲染、Skill 与 `px` 包装；
- 任务说明去掉实验专用的规则段；
- 第三方框架（Pi 或其他）以后按同一接口接入。

**卫生与密钥**：

- Agent 的工作目录只放工作区、任务说明、Skill 与 `px`；
- 服务密钥只在工具进程内读取，传给 Codex 的环境变量中去掉密钥名（`secret_names`）；
- 不读取、不复制 `~/.codex` 下的任何凭据；判断是否可用只看命令行的返回码。

**记录**：

- 文档摘要 `processing.runtime`：`fixed`、`hybrid:agent`，或 `hybrid:fallback`（附原因）；
- `processing.agent`：模型、耗时、按标价折算的费用、工具调用数、修改数、补入数、关闭数，以及处理后剩余的待核对项。

**测试**：用可注入的假 Agent 运行时覆盖：

- 分流与不分流；
- 各种回退：不可用、失败、超时、工作区被改；
- 摘要中的记录；
- 中断后继续。

另加一条真实调用的 Codex 测试，默认跳过（与 `test_live_e2e.py` 同类）。

### 2.2 P4-2 控制台交互（用户补充，Q60）

**原则**：用户随时知道现在在做什么、还要多久、结果如何、出了问题怎么办；安静、不刷屏；在脚本里也好用。

**一次典型运行**（终端里；进行中的行原地更新）：

```
ParserX · 专利说明书.pdf（14 页，其中 5 页扫描）
[1/4] 读取文档                                   ✓ 0.8 s
[2/4] 标准处理
      识别扫描页 5 页 … 服务排队中 12 s
      版面与本地读数 14/14 页
      图片描述 3 张 · 标题与结构 · 检查           ✓ 41 s
      待核对 9 项：标题候选 7 · 页面上有而输出里没有的文字 2
[3/4] Agent 复核（Codex · gpt-6-sol）
      看图  第 4 页（标题候选）
      设为标题  技术领域 → 2 级
      关闭  第 1 页 · 封面信息，不是节标题
      ✓ 2 分 18 秒 · 修改 6 处 · 关闭 3 项 · 剩余 0 项
[4/4] 导出                                        ✓
完成  output/专利说明书/专利说明书.md
      状态 complete · 14 页 · 表格 2 · 图片 3 · 标题 9 · 待核对 0 项
      用时 3 分 01 秒 · 费用约 $0.27（服务 $0.01 + Agent 按标价 $0.26）
      其余文件：专利说明书.json（摘要）· 专利说明书.blocks.json · images/
```

**各种情形**：

| 情形 | 显示 |
|---|---|
| 无需 Agent | 第 3 步显示"待核对 0 项，跳过 Agent" |
| Agent 不可用 | "Agent 未运行：未找到已登录的 Codex CLI（运行 `codex login` 后可用）。已输出标准处理结果，另有 9 项待核对，见 …json 的 review" |
| Agent 失败或超时 | 说明原因与已用时间；输出标准处理结果；待核对项照常列出 |
| 部分完成（partial） | 列出缺失内容的位置与原因（摘要的 `missing`） |
| 服务错误 | 一行说明哪个服务、可重试与否；不打印堆栈（`-v` 才打印） |
| Ctrl-C | "已中断，工作区保留在 …；再次运行同一命令会从中断处继续"（工作区放在固定位置，已完成的步骤不重做） |
| 多个文件或一个目录 | 每个文件一行状态，最后一行合计（篇数、成功、部分、失败、用时、费用） |

**输出约定**：

| 场景 | 输出方式 |
|---|---|
| 终端 | 原地更新的行 |
| 非终端（管道、重定向、CI） | 逐行输出、不刷新，每步一行 |
| `--json` | 结束时把文档摘要的要点写到 stdout |
| 进度 | 一律写 stderr；`-q` 只保留错误与最终结果 |
| `-v` | 附带工具与服务日志 |
| Agent 活动 | 由工具调用翻译成用户能懂的动作：看图、修改、补入、设为标题、拆分、关闭、识别，不显示命令本身 |

**实现**：

- 一个进度事件接口 `Reporter`：阶段开始/结束、步骤计数、等待、Agent 动作、警告、完成；
- 固定流水线的各步与服务等待（OCR 排队）发事件；
- Agent 的动作取自工具调用记录，由工具在调用结束时发出，不靠解析日志；
- 控制台渲染不引入新依赖（ANSI 原地更新 + 非终端降级）；
- 界面语言见 Q60。

**测试**：

- 事件序列 → 渲染结果（终端与非终端两种）的快照测试；
- 回退与中断的提示文字；
- `--json` 的结构。

### 2.3 P4-3 标题的 v2 自有路径（Q59）

- **编号体系的嵌套按出现顺序定**：一种编号样式第一次出现在另一种编号的标题之下，就比它低一级。文档里各种样式的先后决定它们的层级。这样"一、>（一）> 1. >（1）"与"1 > 1.1 > 1.1.1"不用写死任何编号表，都能得到；与已有的点分编号嵌套、同样式统一合在 `unify_levels` 里。
- **排版证据**：先作 `title_candidate`；只有在全语料上验证不降低（D4 的教训：直接采用曾使 4 篇变差），才改为直接采用。
- **v1 标题更好的 8 篇**逐篇按 §9.5 定位：ocr01、ocr_scan_jtg3362、omnidoc_research_report_zh_table_01、paper01、patent01、real_doc01、receipt、text_code_block。能由混合方案解决的（如 patent01）记为已覆盖。
- **adapter:v1 退役**：v2 路径在全语料上 heading_f1 与角色 F1 都不低于 v1 时退役；否则保留到阶段五（Q59）。

### 2.4 P4-4 有信息的图片不丢

- **度量**：语料中被排除（装饰图）或不显示、但有文字（本地读数能读出）或标注中有内容的图片数，目标为 0。度量脚本放 `scripts/`，结果写进报告。
- **路由生效**：UNCERTAIN 与有文字的图片按现有路径转写或描述；只有确认装饰的才排除。
- **统一子文档路径**：DOCX 与 PDF 的嵌入图片走同一路径（Q42 的转写）。

### 2.5 P4-5 DOCX 的页面（Q50、Q9）

- **排版**：经 LibreOffice 排版成 PDF（`content/vector.py` 的 `soffice_env` 已解决中文字体），把段落与表格按文字序列对齐到页和位置，页面图作为资产。有了页面图：
  - 本地读数双向比对可用于 DOCX；
  - `ask_image --page`、`read --image page` 对 DOCX 可用。
- **对不齐时**：该块没有页面位置，功能照旧，并在摘要中计数。
- **Q9**：写出 OOXML 支持边界表（文本框、SmartArt、图表、OMML 公式、脚注、批注、域代码等各自是支持、降级还是不支持），交用户确认。

## 3. 顺序与依赖

```
P4-1 混合运行时 → P4-2 控制台交互 → P4-3 标题 → P4-4 图片 → P4-5 DOCX 页面 → P4-6 专项与逐篇 → P4-7 收尾
```

- P4-1 与 P4-2 合起来是"可以交给用户用"：P4-2 依赖 P4-1 的事件，完成后先请用户试用一次。
- P4-3 至 P4-6 相互独立，可按发现的问题调整先后。
- P4-5 若在排版对齐上遇到大的困难，先报告再决定是否推迟。

## 4. 每项完成时

- 先写测试（合成输入，不用标注内容）；
- 跑 L0 与两个 L1；
- 影响验收文档输出时，空缓存重新冻结并用 `--replay` 验证；
- 更新指导 §12、§15，新决策写入 §14；
- 提交一次（不推送）；报告写入 `eval_reports/`（文件名含日期与阶段号）。

真实的 Agent 运行（验证用）沿用实验装置的卫生规则，每次运行后审计。
