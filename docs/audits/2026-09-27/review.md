## 2. 当前系统做对了什么

实际流程为：输入提取 → 持久化工作区 → 标准处理生成初稿 → 有未解决项或非 complete 时进入 Agent → 工具修改 → 账目检查与导出。

| 部分 | 当前价值 | 应当保留的边界 |
|---|---|---|
| IR 与工作区 | Block、Observation、Anchor、TableGrid、Decision、Evidence、ledger 有明确结构；上下文不承担全文数据库职责 | 源证据应不可变，当前选择不能取代历史来源 |
| 四工具 | 读初稿、看原件、改初稿、交稿，认知边界清楚 | 工具数少并不自动意味着参数、返回及决策成本低 |
| 感知与采用分开 | 重读结果先形成候选，再决定是否写入 | “候选从图像产生”不能自动提升为“候选正确” |
| 固定与 Agent 共用工具 | 能比较流程选择的收益，避免维护两套解析实现 | 默认 fixed/hybrid 的质量差异应单独衡量 |
| 结构化表格 | 网格是主数据，Markdown/HTML 是渲染 | 需要保住行列、表头及数据之间的关联 |
| 调度与缓存 | 在服务边界计数，区分 attempts/cache；并发取得结果、按任务顺序应用 | 金额、跨进程并发和主 Agent 预算仍需补齐 |
| 冻结评测 | 输入/标注哈希、服务响应、输出可追溯 | 回放证明可复现，不证明真实正确或泛化 |

用户希望的“拟人”，最值得落实的是：先了解文档惯例，再提出疑点；选择适当的观察范围；必要时对照原件；修改后检查相关部分。现有 outline、排版类、前后文、局部看图和批量修改已经支持这种方法。

无需为了更像 Agent 而让模型重新逐页转录。适合机器稳定执行的提取、裁剪、索引、计算继续由工具承担；模型主要负责选择证据、解释冲突、推断文档结构。

## 3. 已复现的问题与优先级

### A1 · P1：一次编辑后，原生数字保护会丢失

位置：[content/select.py:235](/Users/xuyun/Projects/ParserX/parserx/content/select.py:235)、[content/select.py:284](/Users/xuyun/Projects/ParserX/parserx/content/select.py:284)。

是否属于原生来源，取决于**当前 chosen_observation 的 engine**。一次获准修改会把 chosen_observation 换为 engine=agent 的候选，后续修改就走非原生分支。

本轮经真实 `call_tool(edit_draft)` 复现：

1. 对原生文字 `采购金额为100万元，不允许延期。` 直接把 100 改成 999：被拒绝。
2. 先将 `采购金额为` 改成 `采购金额：`：被接受。
3. 再把 100 改成 999：**被接受**，没有独立读数支持，引用的合成证据回答仍为 100。

影响：同一段内容先做一个不改变数字的编辑，便可能失去原本要求的核对条件。不能靠提示词约束弥补。

建议：将不可变的源约束与当前采用的读数分开。检查每次修改的来源链及受影响片段，而不是只看最近一次 engine；合法纠错也保留原文、支持证据和明确的被替代关系。补序列测试，而非只测一次修改。

### A2 · P1：表格数字互换仍能通过接受门

位置：[content/select.py:167](/Users/xuyun/Projects/ParserX/parserx/content/select.py:167)、[content/select.py:319](/Users/xuyun/Projects/ParserX/parserx/content/select.py:319)。

数字检查使用全表 Counter，内容保全也主要检查单元格文本是否仍存在。它保住了字符集合，却没有保住“哪个项目对应哪个值”。

本轮构造原生表：`甲=3，乙=20`；候选变为 `甲=20，乙=3`。在 `allowed_cells=set()` 下，具备图像来源记录的候选**被采用，三个 gate 全通过**。

建议：字符纠错在指定单元格范围内进行；结构修复必须显式给出旧单元格到新单元格的映射，并检查来源、表头关联和未授权区域的值不变。允许整行搬移、拆分合并，但不能用“数字一个没少”证明关系正确。原始表的算术错误也要忠实保留，算术核对只产生疑点。

### A3 · P1：证据范围被放大，局部看图可被当成更大范围的支持

位置：[tools/evidence.py:32](/Users/xuyun/Projects/ParserX/parserx/tools/evidence.py:32)、[tools/evidence.py:69](/Users/xuyun/Projects/ParserX/parserx/tools/evidence.py:69)。

当前存在三个尺度问题：

- 接缝图只有上一页下半、下一页上半，`_whole_pages` 却把两页都视为完整覆盖。
- 一个区域只要与块有任意面积重叠就可支持整块，未核对被改字符/单元格是否在可见范围内。
- 指定表格 `rows` 得到的证据，只要 block 相同就通过整块证据检查，没有继续收窄到这些行。

反例中，“第 1 页下半与第 2 页上半的接缝证据”能支持第 1 页顶部块；仅覆盖块边角的微小区域也能通过。

建议：Evidence 保存实际可见的 source spans，包括页、区域、表格行/单元格与变换；修改提交自己的受影响范围，验证前者覆盖后者。还要区分“图像被提供”“视觉回答提出了某个值”“程序校验了这个值”，避免同一个 evidence 编号承担三种含义。

### A4 · P1：重复出现的正文漏识别会被过滤掉

位置：[reading/compare.py:47](/Users/xuyun/Projects/ParserX/parserx/reading/compare.py:47)。

`unaccounted_lines` 收集漏行后，将在两个及以上页面出现的相同文字全部过滤，未要求位于页眉页脚区域或已经被判定为家具内容。

本轮让本地读数在正文位置发现 `必须在加载前锁紧安全装置`，初稿中没有这句话：出现一页时返回漏识别；出现在两页时返回空字典。

影响：这是实际阅读内容的漏检，会进一步影响 `review.open==0` 的分流。重复的表单字段、每章重复的要求、模板正文，都可能受影响。

建议：重复本身只能作为降噪线索。若已有源定位和明确的页眉页脚排除决定，可以据此解释；否则保留为可分组核对的疑点。同类疑点批量处理，既保留发现能力，也控制成本。

### A5 · P2：账目完整和语义核对通过需要分开

位置：[content/select.py:248](/Users/xuyun/Projects/ParserX/parserx/content/select.py:248)、[hierarchy/legality.py:175](/Users/xuyun/Projects/ParserX/parserx/hierarchy/legality.py:175)、[tools/submit.py](/Users/xuyun/Projects/ParserX/parserx/tools/submit.py)。

复现了两种当前允许的行为：

- `不允许延期` → `允许延期`：数字未变，结果非空，所以改动被接受。
- 对一个重要正文块只写 reason、不给证据，执行 exclude；其他块仍有输出时，交稿为 `accepted=true, status=complete`。

第二项符合目前“有理由的排除也算有去向”的契约，不能简单称为账目检查 bug。但它说明 complete 不能被解读为全文忠实、经充分核对。sidecar 保留原文的确有价值，却不能保证只读取 Markdown 的下游不漏掉条款。

建议保留现有处理状态，同时单独记录核对覆盖和关键未决问题；不要要求所有噪声提示清零。对改变否定、单位、数量归属、日期及排除正文的操作，提出更明确的证据要求。独立读数不能仲裁时保留候选或未决状态，不要把“必须与某一个 OCR 一致”升级成唯一真值。

### A6 · P2：当前金额预算是软限制，主 Agent 也没有共用金额上限

位置：[scheduling/budget.py](/Users/xuyun/Projects/ParserX/parserx/scheduling/budget.py)、[scheduling/gateway.py:134](/Users/xuyun/Projects/ParserX/parserx/scheduling/gateway.py:134)、[tools/context.py:69](/Users/xuyun/Projects/ParserX/parserx/tools/context.py:69)、[runtimes/agent.py:91](/Users/xuyun/Projects/ParserX/parserx/runtimes/agent.py:91)。

- 每次预留一个估计金额，完成后才结算真实费用。反例：总预算 $0.02、预留 $0.01，请求最终计费 $0.20，代码正常结算，没有真正的硬上界。
- 主 Agent 主要靠 30/90 分钟截止；token 费用在结束后按配置价格折算，没有纳入工具的文档级预算。
- 不同 CLI 进程各自 preload 同一统计并维护自己的内存锁；若并行调用，预约并不共享。内部单进程批量并发已有保护，应保留。
- unknown 费用在下一次 preload 中用 `or 0.0` 处理，不能将它解释为还有已知的完整余额。
- 工具预算时间不等于端到端时间：主要累计发生服务统计的调用耗时，不包括所有 Agent 思考、纯读取等时间。

建议明确区分：估计费用、已结算费用、未知费用、软目标和硬限制。给模型请求设置可估计的输入和输出上限；统一主 Agent 与服务账本，跨进程预约在同一协调器中结算。先完善统计，再承诺严格预算。金额历史值是按配置价格的估值，不是已核对账单。

### A7 · P2：恢复、回退与累计成本需独立于当前草稿

代码审查发现，恢复时会继续使用 Agent 已改过的工作区，再删除并重建名为 fixed 的导出；若待办已经清空，可能以 fixed 结束。现有中断恢复测试甚至预期这种分类。

位置：[runtimes/hybrid.py:136](/Users/xuyun/Projects/ParserX/parserx/runtimes/hybrid.py:136)、[runtimes/hybrid.py:237](/Users/xuyun/Projects/ParserX/parserx/runtimes/hybrid.py:237)。

此外，失败回退安装的是 Agent 运行前的 fixed 摘要，Agent 阶段的工具服务消费可能没有反映在最终 processing 的服务费用中。恢复后的 Agent 记录也主要描述当前这次运行。

建议将“固定初稿快照”“可继续的 Agent 草稿”“最终已采用版本”分开；成本由不可回退的文档级运行账本累计。即使内容回退，已经发生的消费和 Agent 对最终内容的贡献也不能随之消失。本项是代码路径判断，本轮未重跑完整失败恢复实验，需专项确认。

## 4. 如何避免再次变成规则堆积

建议给现有判断明确分成三类：

| 类别 | 例子 | 应具备的权限 |
|---|---|---|
| 数据与表示约束 | 引用有效、单元格不重叠、坐标合法、不能无记录丢内容、证据不得覆盖到未看到的位置 | 可以硬拒绝 |
| 文档解释的先验 | 同类字号可能同级、连续页同列数可能是续表、某个编号样式通常同级 | 给出候选、冲突及理由，支持有证据的例外 |
| 输出约定 | 标题如何归一化、正文如何显示、页眉是否排除 | 独立配置、冻结后评测，不宣称它就是原件真相 |

当前“同一编号模式同级”“不跳级”被称为 correctness，但在嵌套附件、节选、混合编号文档里，它们也含有语义解释和输出约定。可以保证最终 Markdown 层级合法，但最好同时保留推断的章节父子关系、原文编号和相对层次；不能为了满足表示约束而让模型改错文档关系。

“两种独立证据一致”适合做初稿启发式；版面检测、字号、编号可能高度相关，不能把票数解释为统计独立或置信概率。

还有两处对 Agent 灵活性的实际限制：

- 合表必须先满足 `merge_candidate` 的同列数、相邻页、顺序邻接等条件；这也会挡住原先列分错、跨中间说明或非相邻页的真实续表。应允许先生成结构映射候选，再由内容保全检查核验。
- 当前表格合并不能撤销。Agent 是迭代观察和修正，保留合并前网格及 source mapping，才能撤销错误合并而不必重新解析整篇。

所以新的通用能力应是“带范围、映射和可撤销记录的修改”，而不是增加采购文件、论文、专利各一套处理分支。

## 5. 工具设计的下一步

四个工具继续保留，Q86 的单一契约来源值得完成。之后优先改进以下能力：

1. **让一次读取足够支撑一个决策。** 疑点可附局部初稿、前后文、候选来源、受影响区域和已有证据编号，避免 summary → issues → blocks → source 的机械往返。保持简洁视图，细节按需展开。
2. **按文档中的同类问题处理。** 标题排版类、同一表的多处读数、同页的多个疑点可形成一个核对组。Agent 决定组内规则和例外，工具展开成明确的块 ID 与逐项结果。它解决“理由说要改一类，实际只改一条”，无需再加一层 Agent。
3. **限制返回体量。** text 已有游标；issues、outline 目前仍可能返回全量。增加 token/条目预算和分页，明确显示截断、剩余数量、版本与游标。工具层的“无服务调用”不等于主模型消费这些文本免费。
4. **证据有复用目录。** 同一图、同一问题、同一源版本重复请求时可直接返回已有证据；重读应说明是提高清晰度、扩大范围还是换独立读数。
5. **长文档采用增量计算。** 每次工作区加载/提交都全量读写 state；`unresolved_items` 会进行文档级扫描，批量 dismiss 后又逐项失效重算。先测量 10/100/500 页的 p50/p95，再决定用分区存储、索引、受影响块增量核对还是 SQLite。不要在没有瓶颈证据前重写整个存储层。
6. **比较主 Agent 直接看图与委托 VLM。** 当前产品默认关闭主 Agent 的直接图像观看，以 `answer` 获得视觉回答。它可能省费用，也可能丢掉布局细节、增加往返。只在复杂表格和章节结构上做对照，按成功率与总成本选择，不能从模型单价推断哪种一定更省。

这些建议与官方工具设计资料强调的任务粒度、上下文效率、错误恢复与真实任务评测一致；具体收益必须在 ParserX 自己的数据上测。[Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

## 6. 质量、效率与费用：现有证据支持什么

[阶段五报告](/Users/xuyun/Projects/ParserX/eval_reports/2026-09-26_p5-7_cleanup_exit.md)记录的同批结果：

| 指标 | 固定流水线 | 混合方案 |
|---|---:|---:|
| char_f1 | 0.950 | 0.952 |
| 表格 F1 | 0.866 | 0.875 |
| heading_f1 | 0.699 | 0.697 |
| 角色 F1 | 0.805 | 0.806 |

31 篇里 16 篇进入 Agent，主 Agent 按标价估算 $4.29，服务 $0.05。此轮 Agent 有局部修复价值，但标题净收益近零。它不能证明“更多 Agent 步骤普遍更好”。

[四工具报告](/Users/xuyun/Projects/ParserX/eval_reports/2026-09-27_four_tools.md)针对被选出的 10 篇文档，调用从 364/431 降到 247，Agent 估算费用从 $3.12/$3.32 到 $3.11；s3 标题分数 0.654，s2 两次为 0.671/0.669。该子集固定标题分数为 0.587，说明 Agent 仍可能帮助这类困难文档，但这些数字不能与上面的全语料平均直接相减。

因此可以说：**工具交互更紧凑；稳定降费、质量持平的统计结论尚需更多重复运行支持。** “交稿成功”“待办清零”“卫生审计通过”各有工程价值，都不能替代原件质量核验。

建议每次同时报告：

- 质量：确实修好的问题、引入的新错误、关键内容错误、漏内容、表格关联、章节关系；保留逐篇退步。
- 效率：端到端 p50/p95、Agent 思考时间、工具 CPU/I/O、远程等待、返回 token、输出 token、重复观察次数。
- 成本：主 Agent＋视觉/OCR＋重试＋失败回退＋重跑/恢复的累计费用；冷缓存和热缓存分别测；未知不能记为零。
- 分流：无待办文档抽检漏错率、每类提示的真阳性率、Agent 修复率、引入错误率。
- 单位收益：每个经核实修复的关键问题成本，以及达到同一质量要求的一篇文档总成本。

分流当前只看 `review.open > 0` 或非 complete。下一版可以按问题影响、可修复性、已有证据和预期取证成本分级：便宜的一次核对能解决就停止；证据冲突再升级；没有新增证据的重试设置限额。不要以关闭待办数量作为优化目标。

## 7. 如何验证“更灵活且更省”

建议固定同一份初稿，先做四组增量比较：A 固定输出；B 一次批量模型审阅；C 四工具 Agent；D 同一工具协议的最小函数调用运行时。D 与已有 Q86 计划一致，不需要先建设新框架。

为分清“主 Agent 方法”与“OCR 随机读数”的影响，第一轮复用同一源证据/初稿；第二轮再独立测冷启动端到端费用。主模型、工具、Skill、价格表、标注和指标版本都记录，结果按文档配对比较。

评测需要补三点：

1. **新增真正未见的文档家族。** 现有 phase3_unseen 已按 Q54 转入 ground_truth，并被多轮开发使用。它们仍有回归价值，已经不能继续承担新的泛化盲测。不同格式的同源文件、同模板文件需落在同一拆分。
2. **标注保留版本。** 当前标注修订有理由记录，但旧文件不长期保存。原标注由工具生成、发现错误后修订是合理的；仍应存原文 hash、修订前后版本、修改依据和评测 rubric 版本，用同一版重算所有对照。不要混用不同标题计分范围或不同标注的均值。
3. **困难文档重复运行。** 建议每组至少 3 次起步，报告每篇中位数、最差值及不确定区间；样本不足时明确称探索结果。对没有提示的文档也抽查，而非只看 Agent 被叫醒的文档。

离线回放验证确定性；运行时需要另测“模型能否自主选择有效行动”。Agent 评测同时看过程轨迹、最终产物和环境状态的原则，可参考官方资料。[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

对于小型实验和交互式工具，现有 Codex 适配器足够继续验证方法；若面向无人值守批量服务，最小函数调用运行时还能让预算、工具权限、上下文压缩和重试行为更直接受控。当前 shell、可写工作区和事后摘要校验主要是审计与误操作检测，不能当成独立的权限隔离；接收不可信文档时，源内容中的指令仍应仅作为数据，由工具进程持有服务凭据和写入权限。

## 8. 建议实施顺序与退出标准

| 顺序 | 工作 | 退出标准 |

| 1 | 完成正在进行的 Q86 收口，处理 A1–A4 | schema/CLI/方法说明一致；序列修改、单元格互换、证据越界、重复漏正文反例得到正确处理；本轮接受门与冻结固定输出均验证 |
