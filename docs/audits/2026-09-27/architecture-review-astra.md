- 评审范围：完整流水线、Agent 运行方式、工具接口、工作区与证据模型、处理方法、质量与成本控制；不限于本轮提交。
- 评审性质：架构评审与设计建议，不是逐项实现缺陷清单，也不代表已经完成真实文档质量验收。
- 验证情况：执行离线测试，结果为 **617 passed、4 deselected**；未重新调用线上模型。文中的真实解析效果和费用来自仓库已有的 Q86 测量报告。

**总体判断：本轮架构明显更成熟，现有骨架值得继续保留，没有再次整体重构的必要。接下来最需要解决的是：Agent 能否真正修正初稿的理解方式，以及怎样用有限成本完成这种判断。**

## 1. 应当保留的设计

| 设计 | 评价与保留理由 |
|---|---|
| 持久化工作区保存内容、证据和修改记录 | 应继续作为核心；模型上下文负责当前判断，工作区承担长期状态 |
| `read_draft / view_source / edit_draft / submit_draft` 四个工具 | 动作自然，形成了可理解的工作方式，无须为改进能力而重新命名全部工具 |
| 请求模型生成接口和说明，CLI 与函数调用复用 | 工具开始成为独立产品能力，减少不同运行时之间的语义漂移 |
| 统一角色词表、批量结构修改、修改历史视图 | 更贴近“调整一组章节”的真实任务，减少机械操作和中间状态干扰 |
| 交稿与程序导出分离 | Agent 判断工作是否完成，程序检查状态并负责交付，职责较清楚 |
| 一个主 Agent 配合批量工具 | 当前阶段合理，无须引入更多 Agent 层次 |
| 原件、读数、候选和修改依据留存 | 为复核、恢复和解释提供基础，应继续加强 |

自有函数调用循环也已有采用依据：工具和方法经过实际使用，同一套接口已被第二种运行时调用，并完成了对比测量。此时保留一个薄的自有循环，是合理的工程选择。

需要区分两个层面的独立性：**工具已经基本摆脱运行时的限制；Agent 还没有充分摆脱初稿的限制。** 后者是当前最重要的架构改进方向。

## 2. 流水线与 Agent：保留标准处理，调整介入与调查边界

当前流程大致为：

> 完成标准处理 → 生成初稿和待办 → 必要时启动 Agent → 检查并导出。

这个顺序本身合理。原生提取、常规识别和批量处理适合由程序统一执行，可以减少模型逐步调度的开销。问题主要在两个边界。

### 2.1 待办不应成为发现问题的唯一入口

当前初稿待办为零且状态完整时，程序直接跳过 Agent。结构方法已经要求先理解全文、识别正文与附属部分，但只有 Agent 被启动后，这套方法才能发挥作用。初稿如果“错得很自洽”，可能没有机会接受整体审视。

建议区分两个问题：

1. 程序是否发现了具体异常？
2. 这份文档是否需要一次整体结构判断？

可以根据质量档位、文档复杂度和抽查策略，安排有预算上限的整体浏览。它不必逐页看图，也不必直接进入完整修复循环。待办负责帮助排序，同时保留发现新问题的入口。

这里不建议把所有文档都强制送入昂贵的 Agent 全面复核。介入策略应以质量收益和费用测量为依据。

### 2.2 区分初稿必需处理与可选质量调查

当前标准处理已经提前完成图片描述、部分整页识别等工作。这些步骤可能适合批量执行，但也意味着 Agent 开始判断之前，一部分费用已经发生。

建议逐步区分：

- **形成可用初稿所必需的处理**：继续由程序稳定执行。
- **提高质量的额外调查**：由具体问题、文档需求和预算决定。

哪些步骤适合后移，需要逐项测量。不要假定把全部调度交给 Agent 就能降低成本，也不要将现有固定顺序视为不可调整的边界。

## 3. 工具：补足对错误分块和错误类型的修复能力

当前工具很适合调整标题、顺序、段落连接，修正现有文字和表格，以及核对证据、处理待办。

但当初稿的对象本身划分错误时，表达能力仍然偏窄。例如：

- 原件是一张表，初稿却将其拆成若干普通文字块。
- 两张表被错误合并，后续希望恢复。
- 初稿分块没有恰当的换行位置，却需要重新划分标题与正文。

现有表格重读与采用主要面向已有表格；`split` 依赖块内换行；已经合并的表格不能通过 `unjoin` 恢复。这些限制叠加后，初稿可能提前限定最终答案的范围。

**建议增加围绕原件重新解释局部区域的能力：**

> 选定原件区域或源节点 → 获取新的候选结构 → 检查与原有内容的对应和覆盖 → 接受替换，保留恢复路径。

这项能力应明确限制作用范围，保留来源和旧解释，检查内容去向，并支持恢复。它仍可通过现有 `view_source` 和 `edit_draft` 表达，不必增加一批新工具，也不需要允许模型自由重写整份文档。

同时建议按目标显式返回能力信息，例如：

- 能否查看页面图像？
- 能否查看指定表格行？
- 能否重读为结构化表格？
- 可用的原生结构或其他证据是什么？

本轮将 Word 和特殊表格的限制补入说明是进步。后续让能力随对象呈现，可以减少模型记忆不同输入类型例外的负担。不同格式应如实暴露各自能力，无须为统一接口而假装 Word 已经具备 PDF 式分页视图。

代码依据：[编辑操作与采用接口](/Users/xuyun/Projects/ParserX/parserx/tools/edit.py:117)、[结构修改限制](/Users/xuyun/Projects/ParserX/parserx/hierarchy/legality.py:190)、[原件查看接口](/Users/xuyun/Projects/ParserX/parserx/tools/source.py)。

## 4. 约束：区分硬正确性、文档经验与输出约定

当前部分标题和续表经验直接进入了合法性判断。其风险是：模型已经理解了一份特殊文档，却只能不断调整答案以满足程序预设。

建议明确三类规则：

| 类别 | 示例 | 建议处理方式 |
|---|---|---|
| 必须满足的正确性约束 | 引用存在、顺序无环、内容有来源、修改不能静默丢失内容 | 程序硬检查 |
| 有例外的文档经验 | 同编号模式通常同级；续表通常列数相同且页面相邻 | 候选判断、异常提示，并提供凭证据处理例外的路径 |
| 产品输出约定 | 标题是否规范为连续层级、界面文字是否排除 | 统一且明确的输出契约 |

例如，“标题不得跳级”如果是明确规定的 Markdown 规范化要求，可以保留；但应区分原件结构和输出表达。“同一种编号一定同级”则需要可靠的作用范围，不能假定所有文档都遵循同一种组织习惯。

“流水线不得覆盖 Agent 的结构判断”保护了已审阅工作，方向正确。不过长期来看，判断的权威性还应关联证据、范围和版本。新证据出现时，可以重新开启冲突并要求复核；仅凭修改者身份永久锁住判断，会限制后续纠正。

这不意味着允许流水线无条件覆盖 Agent，也不意味着撤掉安全检查。目标是保留明确的内容保护，同时让语义判断能够随证据更新。

代码依据：[续表与结构合法性](/Users/xuyun/Projects/ParserX/parserx/hierarchy/legality.py:214)、[Agent 决定保护](/Users/xuyun/Projects/ParserX/parserx/hierarchy/legality.py:247)、[层级约束](/Users/xuyun/Projects/ParserX/parserx/hierarchy/legality.py:268)。

## 5. 状态：增加轻量的文档理解记录

当前结构方法值得保留：先浏览全文，分出正文与附属文件，识别各部分惯例，按类调整，再处理例外。

但这些重要结论主要留在模型上下文和分散的修改理由中。工作区保存了块、证据、关系和决定，却没有清晰承载“这份文档目前被如何理解”的位置。

建议增加一个轻量记录，例如：

> 第 20—35 页是独立附件；这里的“一、二、三”属于附件一级标题；依据为附件题目、目录和抽查位置；还有两处例外待确认。

记录至少表达：

- 适用范围；
- 当前判断或结构惯例；
- 证据引用；
- 尚未解决的问题；
- 必要时重新审视的条件。

这些记录应明确属于可修订的解释，与原件事实分开。无需为此建设复杂知识图谱、通用记忆系统或新的大型框架。

预期收益是长文档处理、断点恢复和上下文压缩。内容持久化之后，Agent 对内容的理解也应能够保留，避免反复重建。

代码依据：[结构方法](/Users/xuyun/Projects/ParserX/parserx/skills/structure.md:9)、[工作区状态](/Users/xuyun/Projects/ParserX/parserx/ir/state.py:123)。

## 6. 效率：优先优化模型读取量和判断轮次

Q86 报告给出了有价值的测量信号：

| 指标 | 报告结果 |
|---|---|
| 相同模型下 Agent 总用时 | 新接口 Codex 为 459 秒，自有循环为 315 秒 |
| 自有循环的耗时分布 | 模型约 265 秒，工具约 49 秒 |
| 自有循环调用量 | 5 篇合计 54 轮模型调用 |
| 自有循环累计输入 | 约 198 万 token，其中 89% 命中缓存 |
| 便宜模型的表现 | 能完成流程，但标题质量下降 |

这些数据支持继续验证自有循环，并提示当前优化重点应是上下文组织与决策轮次。

当前循环持续累积模型输出和工具结果，每轮带回历史。因此，“读初稿不产生外部识别费用”不等于“读初稿没有模型成本”。工作区持久化与上下文长度受控，需要分别实现。

建议优先考虑：

1. 用文档理解记录保留稳定结论。
2. 每轮只读取与当前判断有关的材料。
3. 围绕一组章节、一类版式、一个争议区域组织调查和修改。
4. 没有新证据时停止重复读取和修改。

缓存已经发挥作用，压缩上下文也不必然更便宜，应测量总费用、耗时和质量。优化目标是每次付费读取与判断带来的质量收益，工具调用数只是辅助指标。

**测量边界：** 报告各配置每篇只运行一次，不能据此确认运行时或模型的质量稳定性。工具限制说明的修正在测量之后，尚未复测。当前结果足以支持接口可迁移及后续实验，不足以宣称新方案在所有文档上更优。

资料依据：[Q86 测量报告](/Users/xuyun/Projects/ParserX/eval_reports/2026-09-27_q86_interface.md:10)、[上下文累积方式](/Users/xuyun/Projects/ParserX/parserx/runtimes/loop.py:56)。

## 7. 产品定义：形成统一的输出契约

系统同时承担忠实转录、正文清理和图片语义补充。当前已经明确图片描述不修改正文，并区分可见、估读和推断，这是值得保留的设计。

以下行为则属于产品对解析结果的定义：

- 截图中的界面文字是否排除；
- 被遮挡但存在于原生文字层中的文字是否保留；
- 标题层级如何规范化；
- 原件内容与模型补充说明如何区分。

这些约定目前部分散落在处理方法中。建议形成简短、统一的输出契约，让流水线、Agent、渲染和评测遵守同一套定义。先有一个清晰的默认行为即可，不需要立即增加大量配置。

同时，待办清零、程序处理完整和实际解析正确，应继续作为不同层面的信息呈现。一次抽查覆盖了哪些内容、哪些地方仍未核实，不能仅由待办数量代替。

资料依据：[忠实转录方法](/Users/xuyun/Projects/ParserX/parserx/skills/transcription.md)、[图片理解方法](/Users/xuyun/Projects/ParserX/parserx/skills/figure.md)。

## 8. 下一轮优先级与验证建议

如果只选择三项进入下一轮，建议顺序如下：

| 顺序 | 架构改进 | 预期解决的问题 |
|---|---|---|
| 1 | 补足局部重新解析与恢复能力 | Agent 能修正初稿错误的分块、类型和合并 |
| 2 | 明确硬约束、文档经验与输出约定 | 程序保护来源和完整性，同时允许有依据的语义例外 |
| 3 | 持久化文档理解，控制上下文与调查预算 | 长文档可持续处理，减少重复阅读和重复判断 |

建议用以下场景验证设计上限，而非只测常规文档是否顺利交稿：

| 场景 | 需要验证的能力 |
|---|---|
| 表格被初稿识别成普通文字 | 能从原件恢复表格结构，保留文字、数值与来源对应，不产生重复内容 |
| 两张独立表格被误认为续表 | 能恢复合并前的解释，并重新确定关系 |
| 正文附带多个独立文件，编号重新开始 | 能按范围建立结构惯例，不将局部规则错误推广到全文 |
| 初稿无待办但存在整体结构错误 | 在约定的质量策略下仍有发现问题的路径，并能测量额外成本 |
| 长文档中断后继续处理 | 保留已有理解和证据，避免从头阅读，并正确重开受新证据影响的判断 |

架构能力验证通过后，再用冻结的工具、方法和评测口径，在未用于调试的文档上进行重复测量。分别记录质量、未决问题、模型与工具费用、耗时和人工干预，避免将流程跑通等同于质量达标。

**最终评价：运行时与工具之间的边界已经比较成功。下一步最有价值的工作，是让工具能够表达更完整的修正意图，让程序保护来源与完整性，同时给 Agent 足够空间重新理解文档。**
