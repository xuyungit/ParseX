## 2. 时间花在哪

- **模型时间占 Agent 时间的 93–98%，工具执行只占 2–7%。**
  - Codex 4 次：模型 1340 秒，工具约 100 秒。
  - 循环 4 次：模型 826 秒，工具约 30 秒。
- **按下一步要做的事分（模型时间，4 次合计）**：

| | 改（edit_draft） | 读草稿（read_draft） | 看原件（view_source） | 消息 | 脚本 |
|---|---|---|---|---|---|
| Codex | 553 秒 / 23 次 | 422 / 53 | 137 / 17 | 205 / 18 | 11 / 7 |
| 循环 | 108 / 12 | 300 / 69 | 392 / 35 | 21 / 4 | – |

- **单步很慢的是"想好一大批改动"的那一步。**
  - Codex：照图重写一张表之前 105 秒；一次定 35 个、24 个标题角色之前 62 秒、50 秒；一批改字加关闭之前 72 秒。
  - 循环：看公式页图片后的那一步写出 1–9k 推理 token（DeepSeek 约 250 token/秒，即 5–39 秒）。循环的单步时间与这一步的输出 token 成正比，与上下文大小关系不大。
- **思考强度**：Codex 降到 low 不稳定地更快（两次 391、665 秒，medium 449–806 秒）。

## 3. 无效的尝试：工具设计导致的

按出现次数和代价排列（13 次运行合计）：

1. **一个操作的格式错，整批作废。** `edit_draft` 先整体校验请求，一个操作不合格，整批 19–22 个改动全部被拒。之后 Agent 要重新想、重新写这一批（多一步长思考，30–70 秒）。
   - 整批作废共 11 次（Codex 7、循环 4）。
   - 新跑的 4 次 Codex 每次都撞上：`note` 的 `evidence` 是列表，其他操作的 `evidence` 是字符串（"ops.N.note.evidence: Input should be a valid list"）。这是我们接口不一致。
   - 循环：DeepSeek 自己加了不存在的字段（`reason_extra`、`block_note`、`scope_note`）。
2. **Word 文档图片里读出的表格不能按表格重读。**
   - `view_source as table` 对它说"DOCX 的表格是原生的、没有页面图像"（5 次）；对图片块说"这是图，不是表"（4 次）。
   - Agent 只能照图一格一格重写整张表：speed_bid01 的所有者权益变动表 26 行×12 列，Codex 每次都要用 4–5 分钟。中间 set_table / set_cells 被拒 3–5 次（单元格重叠、越界、"只改结构时字不能少"），每次再想、再写。
   - 区域重读这条路本来就有（PDF 扫描页可以），只是没有接到 Word 的图片上。
3. **Word 文档的"页"含义不一。**
   - 视图给 Word 文档的每行标 `page`（其实是分段号）；`insert_text` 却要 PDF 页号。
   - 循环 11 次插入被拒（"no PDF page 11"），只好改用别的写法。
   - 看原件时也有同类问题："Word 文档没有页面图像，只能看图片块" 7 次，"不是带图片的图" 3 次。
4. **关闭待办时证据不对。** "e-… 不是这一块或这一处的证据：先看它"，共 11 次。Agent 拿看别处的证据关这一项，要再看一次、再关一次。
5. **编号**：
   - 同一块上的几项待办共用一个编号（4 项表格算术都是同一个 w-…）。
   - Agent 猜不存在的块编号（"no blocks b-d00142-r004 …"）5 次。

## 4. 返回太多，逼出脚本和长思考

**各视图返回的字数（13 次合计）**

| 视图 | 次数 | 平均 | 最大 |
|---|---|---|---|
| read_draft blocks | 29 | 16k 字 | 118k |
| read_draft outline | 10 | 21k | 42k |
| read_draft text | 49 | 7.6k | 49k |
| read_draft issues | 15 | 5.6k | 15k |
| view_source image | 44 | 1.3k | 4.9k |

- **表格在 blocks 视图里是每格一个 JSON 对象。** 每个对象带 `row`/`col`/`rowspan`/`colspan`/`is_header`/`content{doc_text}`，一格"序号"两个字要约 100 字的外壳。一张表 55k 字，四块 118k 字。
- **Codex 应付大段 JSON 的办法是写脚本。** 先把输出存到 /tmp，再用 `./px python` 挑字段：之前 5 次共 22 个脚本，脚本之前的模型时间合计 320 秒。新跑的 4 次只剩 7 个，因为重读能用了，不必再拼表。
- **循环一开始就把全文分 9–12 段读完（约 7–10 万字）。** 之后每一步都带着 13–20 万 token 的上下文。它看公式页时一次只看一张图（paper_chn01 连续 13 次单张看图），同一页看了两三遍：清理上下文后图片没了，又看一次。

## 5. 工具自身的效率

都不是主要问题：

- **Codex 每次工具调用都起一个 `px` 进程：** 比工具自身多 0.3–0.8 秒。
- **改草稿：** 一般 1–2 秒，主要是每次读、校验、重写 2.4 MB 的 state.json。改字要请 DeepSeek 重读时 9–11 秒。
- **看原件：** 纯看图 0.1–0.5 秒；提问（answer）、重写说明（description）要请服务模型，2–13 秒。

## 6. 有效的部分

- 看原件大多被用上：看图拿到的证据，大部分后来被接受的改动或关闭引用。Codex 一次看多张，循环在 paper_chn01 上 15 次看图里有 5 次没被引用。
- 改动的接受率高：被拒的多是上面那几类工具问题。剩下的才是正当的拒绝，例如"已经接上了""删了这块会让别的内容没处显示"。
- 质量：Codex 在公式和表格文档上更好（paper_chn01 关键 43 对 72，unseen_pdf_tables01 0 对 5——循环把表改坏了一处）；循环在 Word 和扫描文档上快一半以上。

## 7. 可以改的地方

都不改变 Agent 的形态：工具仍是原子的，Agent 仍自己决定读什么、看什么、改什么。按预计省下的时间排：

1. **改草稿逐个操作校验，字段写法统一。**
   - 不合格的操作单独被拒，并说明是第几个、为什么；其余照常处理。
   - `evidence` 在所有操作里接受同一种写法。
   - 每次运行少一次重想重写，约 0.5–1 分钟；改动小。
2. **Word 图片里的表格可以按表格重读。** 让区域重读也接到图片的区域上，与 PDF 扫描页一样。Agent 不必照图手抄整张表：遇到时省几分钟，也更准。
3. **视图紧凑一些。**
   - 表格写成按行的格子（每行一个数组，合并格标出跨度），不是每格一个对象：同一张表约小 5–10 倍。
   - outline 与 text 视图按需过滤（只看标题、只看有待办的行、一个页段）。
   - 返回少了，Codex 就不用写脚本，每一步也想得更快。
4. **Word 文档的位置说法统一。** 视图里标"段"而不是"页"；插入文字可以用"在某块之后"，不必给 PDF 页号。看原件时直接说清楚 Word 文档能看什么。
5. **待办编号一项一个。** 同一块上的几项各有编号。
6. **自己的循环。**
   - 一次回复里的多个工具调用并行执行（现在是一个接一个）。
   - 看过的图在清理上下文后留一个"看过、结论是……"的记号，免得同一页反复看。
7. **任务说明**里写清：看图可以一次看多张；交一批改动前先对照工具参考里的字段。哪些写进说明、写多少，由用户定（措辞对 Agent 的影响以前试过很小，Q81 后的经验）。

第 1、5 项是接口缺陷，可以直接改。第 2–4 项是工具设计的改动，也是本节的主要收益。第 6 项只涉及自己的循环。第 7 项需要用户决定。
